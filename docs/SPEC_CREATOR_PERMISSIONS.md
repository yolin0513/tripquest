# SPEC（草稿）：建立者專屬權限（creator-only）

> **狀態：評估／待決，未立項。** 骨架草稿。更早的工作階段評估過，**全文已隨對話壓縮散失**，
> 此檔只保留問題陳述與待決點。要推進的話**依開發流程慣例開 3 個 Fable 代理重做評估＋投票**。
> 最後更新：2026-09-18。

## 為什麼被提出

目前 trip 的設定任何成員都能改。有人問：某些設定（尤其破壞性的）是否該**限定「建立者」才能改**，
避免旅伴誤動或家中舊裝置誤觸。

## 待決問題（要做之前必須回答）

1. **建立者識別可不可靠**：能不能用 `createdByDevice`（或等價欄位）穩定判定誰是建立者？
   - 換手機／清資料／重裝之後，原建立者會不會就失去身分？需要 fallback（例如可轉移建立者）。
   - 現行資料模型裡這個欄位存不存在、可不可信，要先查證再設計。
2. **哪些設定重要到需要保護**：刪除旅程、改動行程結構（景點／天數）屬高風險；一般協作
   （拍照、記帳）不該擋。要畫清「受保護設定」的界線。
3. **對長輩的影響**：多一層權限＝多一層卡關與「為什麼我不能改」的困惑。家庭情境的信任成本本就低，
   權限模型要非常克制，寧可用「二次確認」而不是「硬擋」。

## 相關現況（STATUS.md 既有記錄）

- 家中若有裝置停在 v1.61 以前，按「刪除旅程」會同步刪給所有人——這正是「破壞性操作該不該只給
  建立者」的實例；但當時的解法是請家人更新 App，而非加權限。
- 邀請連結永久有效、無成員移除——若要做權限，得一併想「拿過連結的人」算不算成員。

## 我的建議

**先不做**（見 STATUS.md 開頭「等 Yolin 回覆」⑤）：多一層權限對長輩是負擔，家庭情境信任成本低。
若要做，先開 Fable 代理投票，且第一步必須是**查證 `createdByDevice` 到底可不可信**——不可信的話
整個方案的地基就不成立。
