## 工作慣例（常設規則，給每一個接手的工作階段）

**1. 重大決策要三個代理獨立投票。** 架構選型、資料結構、部署方式、需付費或需註冊帳號的
服務 → 由統籌者開 **3 個代理**（與統籌者同模型、同 effort，照共用慣例 §1.4）、同一份 prompt、
各自獨立、多數決；分歧時採保守方案；決議寫進回報與這份文件。

**2. 模型或額度不可用就整批改用同一個可用的模型，不要停下來問。**（「不要停下來問」是使用者
2026-09-10 明訂；2026-09-23 起不綁特定模型，照共用慣例 §1.5）

- 代理因額度或速率限制（429／quota）失敗 → **整批改用同一個可用的模型重跑**，
  不需要再問使用者。
- **整批重跑，不要只補跑失敗的那幾個** —— 投票要在同一個模型上才可比。
- 事後在回報最前面註明實際用了哪個模型與 effort、原因，讓使用者知道這一輪的背書是誰做的。
- **連一個可用的模型都沒有時**才回報並暫停。

理由：額度用盡是暫時性的環境狀況，不是需要使用者決策的事；真正需要他決策的是投票結果。
為了這種事停下來等回覆，等於把一個環境問題變成一個人的問題。

*已套用*：v1.66 那輪與 v1.73 這輪的全面健檢，Fable 額度都用盡（實測 429），
七個代理全部改用 Opus 5 執行（當時的模型設定）。

**3. 每版的流程**：bump `sw.js` VERSION → `npm run test:affected`（底線＋受影響，見下面
「測試」節的「測試範圍」）→ commit → **`bash scripts/safe-push.sh` 推送**（公開前自查＋推送＋比對遠端，
不要自己 `git push`；見下面「推送閘」）→ curl 確認線上 VERSION → `npm run sweep` → 截圖放
（推送之後那幾步**用 `&&` 接在推送閘後面**、不接管線：`bash scripts/safe-push.sh && <curl 確認線上 VERSION> && npm run sweep`——
推送閘任何一關失敗，後面的線上確認就不會跑，免得對著沒推上去的舊版驗、看起來還是綠的；共用慣例 v7 §2.5）
`screenshots/features/` ＋鏡像資料夾。**全面檢測（完整 `npm test`＋`sweep`）由 Yolin 指定才跑**
（2026-09-19 裁示）；回報與 commit 訊息**不准把部分測試寫成「全綠」**，要寫「底線＋受影響 N/M 支綠」，
回報最後附「距上次全面檢測：N 版／D 天」。
**動到 `js/merge.js` 或 `workers/` 時：Worker 先部署、客戶端後推**（v1.73.2 實測，
反過來會造成永久分歧）。

## 開發流程慣例（常設規則，Yolin 2026-09-14 明訂；模型與 effort 2026-09-23 改定）

**1. 規劃階段（統籌 Session）**：由共用的統籌 Session 負責理解 Yolin 的需求、拆解並寫成規格。
規格檔放在本 App 的 `docs/SPEC_<主題>.md`。模型與 effort 照共用慣例 §1.1。

**2. 開發階段（開發 Session）**：模型與 effort 照共用慣例 §1.2（平常 medium，重大任務可上調 high；

也負責查找／蒐集資料。

**3. 流程**：統籌者寫 spec → 開發 Session 實作＋查資料 → 回報並逐條與需求（spec）對照 →
與 Yolin 確認。

**4. 較大改動或值得討論的議題**：由統籌者開 3 個代理投票；各代理當統籌，
把查資料的工作交給勘查代理；統籌者彙整投票結果再回報。
（與上面「工作慣例」第 1、2 條並行：代理與統籌者同模型同 effort，額度不可用時整批改用同一個可用的模型。）

**5. 測試紀律不變**：照既有慣例——回歸斷言要用突變測試證明會紅、不寫假斷言、
測試要走使用者的真實路徑、回報區分「實測驗證過的」與「推論的」。

**6. 不准用互動式提示框／多選題工具**（`AskUserQuestion` 之類）。（Yolin 2026-09-16 明訂）

需要使用者決定的事，一律**用純文字寫在回覆裡**：清楚列出選項、講出你的建議與理由，
然後**停下來等**。答案會由 Dispatch 轉達給使用者、再把回覆帶回來。

理由：使用者常從**手機或另一台電腦遠端**操作，互動式提示框只渲染在本機那台 PC 上，
遠端點不到 —— Session 會直接卡死，沒有人能往下走。

**7. 全程用繁體中文書寫。**（Yolin 2026-09-16 明訂）

**思考／判斷過程的文字敘述**與**回覆**都用繁體中文，包括：為什麼這樣做、
列出的選項與建議、進度回報、結論。

**維持原樣、不用硬翻**：程式碼、變數與函式名、檔名與路徑、專有名詞、
引用出處（指令輸出、錯誤訊息、原始碼註解、外部文件的原文）。

理由：使用者要能**清楚跟上推理與取捨**，而不是只看到結論。判斷過程用外文寫，
等於把最需要他評估的那一段藏起來。

## 重要架構決策（含理由）

1. **欄位級合併（v1.56，三代理 3:0）**：`js/merge.js` 純函式，客戶端／Worker／LAN server 三處同一份。spot/trip/quest 帶 `_f`（欄位組→時間戳），組＝一起寫的欄位（slot=day+order、time、pos=座標+來源、name、pinned…）；pos 手動優先；刪除/新增整筆語意；舊記錄退路＝updatedAt＋首次觸碰播種齊全；伺服器 no-op 不佔 seq、樂觀鎖重試、/push 回 merged；時間戳單調 max(now, prev+1)。理由：家庭規模下版本向量/op log 過重，per-field LWW 最小夠用。
2. **AI 金鑰只存本機**（tripSecrets 獨立 store，不進 exportGroup/exportRecords/同步）：金鑰洩漏面最小化；瀏覽器直連供應商，Worker 不經手。
3. **音樂放 R2 不放 repo**（v1.55）：曲庫再大不肥 repo/預快取；Worker 唯讀端點＋獨立 tq-music-v1 快取（升版不清）；repo 只留 playful.mp3 當離線保底；R2 取不到→退回合成音樂並明講。授權兩輪三代理查證（3:0），CC BY 維持 6 首不擴大，古典逐首查「錄音本身」授權（Clair de Lune 因錄音是 CC BY 3.0 被剔除換 WTC）。
4. **免金鑰資料源**：Nominatim（1.1s 節流＋30 天快取＋viewbox 偏好＋站點降權＋維基別名補候選）、FOSSGIS OSRM（1rps、一天一矩陣、canonical 快取）、Overpass（SOS 附近設施）、Open-Meteo、zh.wikipedia。取捨：無評分/營業時間/人氣——誠實標示，付費升級路＝使用者自帶 Google Places 金鑰（已擱置）。
5.6 **SW 換版一致性（v1.59.1）**：SHELL 檔案改「本版快取釘死的 cache-first」——先前的 stale-while-revalidate 會把網路新版寫回正在跑的版本快取，造成舊 app.js 配新 trip.js（畫面有新入口、路由表沒有那條路→被踢回首頁，v1.59 實機踩到）。換版只走 install addAll(cache:'reload')＋SKIP_WAITING 整組換；另加保險絲：notFound 時 /trip/<id>/* 退回該行程頁。nearbytest 有路由完整性稽核（view import ⊆ SW SHELL、navigate 目標 ⊆ 路由表）。
5. **原生 PWA、無框架無打包**；IndexedDB＋版本化 SW；h() 全 textNode＋URL 白名單（無 XSS 面）；CSP script-src 'self'。
6. **iOS 教訓**：原生 time input 空值畫成當下時間＋寬度不可控 → 全 App 改時/分下拉；主畫面 App 與 Safari 儲存分離 → 邀請流程 iPhone 先裝後加入。
7. 外部請求全部有逾時（AbortSignal.timeout 守門），失敗走各自降級（v1.55.1 健檢）。
12. **即時感（v1.63）**：實機回報「B 加入了，A 停在任務頁一直沒看到」「兩台都開位置分享卻互看不到」。三個獨立根因：①**建立者從來沒有 memberClaim**——建立流程不會問「這是誰的手機」，所以旅伴看到「建立者未加入」（資料面對、語意錯），而且 `pos.updateNow` 找不到 activeMemberId 就直接 return，**他的位置永遠傳不出去**（這也解釋了「A 重啟後 B 才看到 A」：重啟後那顆軟性按鈕被按了才有 claim）→ `claimAsCreator()` 在建立當下就問一次（單一成員直接認領），舊行程進行程頁時補問。②**背景 pull 固定 90 秒**且開頁不觸發 → 前景 20 秒／背景 90 秒，並在行程頁、SOS 頁、照片牆開啟時 `refreshNow()` 立刻拉一次。③**行程頁只在「現在這一站」或 claim 數變動時重繪**，旅伴新增的景點/照片不會讓畫面更新 → 改看一份輕量內容簽章（景點數、任務數、照片數、成員數、最大 updatedAt）。誠實提示：PWA 沒有推播，所以是「每 20 秒去問一次」，旅伴清單與 SOS 頁都給了「立刻更新」按鈕。**兩台裝置實測（livesynctest）**：看到有人加入 17.0 秒、打開 SOS 看到對方位置 0.5／0.0 秒、旅伴新增的景點 18.5 秒自己出現（修正前全部逾時 >45 秒）。
11. **移除旅程＝只影響這台裝置（v1.62，三代理 3:0）**：舊版的「刪除旅程」是同步刪除——任一成員按下去全家的行程與照片一起消失（使用者實機踩到）。現在 `store.forgetGroup()` 硬刪本機記錄，**不寫墓碑、不排同步**。三個必修細節（三位代理各自獨立指出）：①**記憶體與 IndexedDB 必須一起清**——`importRecords` 結尾是 `db.putRecords([...state.byId.values()])`，只刪 IndexedDB 的話下一次任何同步都會整趟寫回來；②**drain 競態**——群組清單是迴圈開始前的快照，所以加了 `forgotten` 名單＋`outbox.idle()`＋迴圈內重查；③群組底下還有別的行程時只清這一趟。另清：outbox 待送項（殘留會讓 drain 每 2 秒空轉）、`seq:<gid>` 游標（不歸零則日後還原只拿得到殘缺的一半）、tripSecrets、全部 per-trip/per-spot localStorage 旗標；先 `pos.stopSharing` 再移除。**未上傳的照片會擋門**（只有這台有）。**祕鑰留在本機 meta**（不同步、不匯出）→ 設定頁「已移除的旅程 → 加回來／徹底忘掉」，長輩不用去 LINE 翻連結。文案分支：有同步→「其他旅伴不受影響」；單機→「移除等於永久刪除」並引導先匯出備份。**不提供全群組刪除**（沒有帳號系統，「建立者」只能靠可被覆寫的本機欄位判斷，撐不起這種權限）、**不忽略外來墓碑**（刪一個景點是日常操作，忽略會壞掉；三代理一致）。舊版並存：舊版裝置按刪除仍會影響所有人，直到它更新——這點無法從新版擋住。
10. **貼地圖連結取位置（v1.61）**：`parseCoordInput` 支援 Google 完整網址（@／!3d!4d／ll／center）、Apple 地圖（ll／sll／daddr）、`geo:` URI、純數字（全形逗號／空格）、多行分享文字。**短網址**（maps.app.goo.gl）本身不含座標 → Worker `/resolve` 跟隨轉址；**只讀 location 標頭、永不讀內容**：既不當內容代理，也避開實測到的陷阱——Google 地圖 HTML 裡的 `center=` 是**預設地圖中心**（貼蘇澳的連結、HTML 卻寫台北），讀 HTML 會給出「看似合理其實全錯」的座標。不跟進 `/sorry/`（Google 對雲端 IP 的機器人驗證頁，其 `q=` 是內部 token）。轉址後常只有「地址＋店名」→ `placeCandidates` 依「像不像地標名」拆解（地名字尾優先於地址判定、去掉「國道五號」這類前綴、丟掉切壞的碎片、3 字 CJK 地名不降級），多候選結果**合併後用原文的鄉鎮名評分**（實測兩個坑：先中的候選給了 3 公里外的飯店、22 公里外的同連鎖分店），且**一律讓使用者確認**、可自己改搜尋詞。失敗訊息列出三種可貼格式並教「在地圖上長按會出現座標」；離線時明講要連線。
9. **旅伴位置分享（v1.60，三代理 3:0 GO-with-changes，必修項全數落地）**：新型別 `memberPos`，id = `pos:<tripId>:<memberId>:<deviceId>`（多裝置不互蓋），走整筆 updatedAt LWW（**不進 APPEND_ONLY** —— 那是「已存在就跳過」，位置會停在第一筆；也不進 TRACKED）。座標降到小數 4 位（~11m，帶 accM；>300m 只說「大約在附近」）。**隱私三道**：①`store.exportRecords()` 預設排除 SENSITIVE_TYPES（全 App 35 處通用資料源自動乾淨，只有 exportGroup 明確包含）②關閉/過期寫**不含座標的墓碑**（`store.remove` 是 patch 展開語意，會把 lat/lng 留在墓碑裡——這是「我關掉了啊」最會被背叛的地方）③伺服器 48 小時 TTL：Worker cron 每日把過期的改寫成無座標墓碑並佔新 seq（**不是 DELETE**——客戶端游標是 seq，刪列的話別台永遠不知道要清本機副本），pull 端另有即時保險；LAN server 同一套。**單筆推送**（一般 put 會把整個群組幾百筆推一遍）。同意畫面講五件事（誰看得到＋實際名字／看得到什麼／多久／怎麼關／關了會怎樣）、行程頁常駐指示、SOS 頁一鍵停止。文案誠實：PWA 無背景定位 → 一律講「最後一次打開 App 時的位置」，不講即時追蹤。

## v1.74.3 表單的一排按鈕不再包在 `<label>` 裡（`SPEC_分帳金額守恆.md` R0）

**使用者現象**：記帳時「誰付的」「分類」點哪一個都跳回第一個 → 每一筆都記成第一個人付的餐飲。

**根因**：三個頁面各有一份一模一樣的 `field()`，回傳 `<label class="form-field">`。label 會把點擊轉發給
裡面第一個可被標記的控制項（`<button>`、`<input>`、`<select>` 都算），有兩條路會中：
① 被點的按鈕在 `onclick` 裡重繪、離開 DOM，點擊冒泡到 label 時它已不是 label 的子孫，label 就去點第一顆；
② 手指落在標題字上，label 直接去點第一顆。

**修法**：包「一組控制項」的改用新的 `fieldGroup()`＝`<div class="form-field" role="group" aria-label>`；
包單一輸入框的維持 `field()`（`<label>`，點標題字聚焦輸入框是對的）。class 不變、版面不變。
三個檔逐一盤點的呼叫點：

| 檔 | 欄位 | 包的是什麼 | 處理 |
|---|---|---|---|
| `expenses.js` | 這筆是什麼 | 單一 input | 維持 `field` |
| `expenses.js` | 分類／誰付的 | 一排會重繪的按鈕 | → `fieldGroup` |
| `expenses.js` | 分給誰 | 每人一個巢狀 `<label class="exp-part">`（勾選框＋份數框）＋切換鈕 | → `fieldGroup` |
| `create.js` | 旅程名稱／直接貼上行程文字 | 單一 input／textarea | 維持 |
| `create.js` | 哪幾天去？ | 單一按鈕（開月曆） | 維持 |
| `create.js` | 有誰要一起 | 旅伴 chip（每個有「×」，會重繪）＋輸入框 | → `fieldGroup` |
| `spot.js` | 景點名稱／停留多久 | 單一 input／select | 維持 |
| `spot.js` | 幾點到 | 兩個下拉＋「清除」鈕 | → `fieldGroup` |

全 `js/views/` 其他的 `<label>`：`switch-row`（只包一個勾選框）、`import.js` 的 `imp-chk-w`（只包勾選框）、
`findspot.js` 的三個（下拉，沒有按鈕、不重繪）——查過，沒有同型寫法。

**修正前實測到、規格沒列的兩件（都是同一個根因，這一版一起修掉）**：
- 分帳表單點「分給誰」三個字 → **第一個人的勾被取消**，那一筆就少一個人分（使用者看不出來）。
- 建立旅程點「有誰要一起」四個字 → **第一位旅伴（預設的「我」）被刪掉**。`create.js` 裡那段
  「350ms 內擋第二次觸發」的註解描述的「殘留點擊落到移位後的鄰居身上」，很可能就是這條路①。

**「分給誰」點名字、點勾選框、在份數框打字**：修正前後都正常（巢狀 label 裡點擊落在內層 label，
不會傳到外層）；壞的只有點標題字那一條。

**測試**：`settletest` 改成最後用真的滑鼠從表單記兩筆（T0／T0b，44 項）；新增 `formgrouptest`（12 項）。

## v1.74.2 算錢的測試（規格 `docs/SPEC_算錢的測試.md`）

## v1.73.6 選音樂就被彈回任務頁（使用者實測）

使用者回報：**「回憶影片只要點選任何音樂就會跳回到任務頁面，不管是配樂或是合成音樂」**。

### 線上重現

```
點之前  hash=/album   畫面=相簿／影片頁
點之後  hash=/album   畫面=**任務頁**   標題變成行程名
```

**網址沒變、畫面被換掉** —— 所以不是 `navigate()` 導走，是 `trip(tripId)` 直接畫上去。

⚠️ **第一次重現失敗**：直接 `goto('#/trip/<id>/album')` 點音樂完全正常。
必須走使用者的真實路徑（先開行程頁 → 回顧 → 相簿）才會發生 ——
因為 `watchHere()` 只有行程頁會註冊。

### 根因

`js/views/trip.js` 的 `watchHere()` 訂閱 store 之後**從來不取消**，只靠一份
hash 的**排除清單**擋：`spot|plan|poster|weather|people|expenses|memories`。

- 清單漏了 `album`
- `store.patch({ musicStyle })` 會 bump `trip.updatedAt`，而那正好在
  `tripSignature()` 的 `maxUp` 裡 → 簽章一變就呼叫 `trip(tripId)` 重畫整頁

**線上逐頁實測，受影響的有 7 個**：`settings`、`album`、`findspot`、`sos`、
`nearby`、`badges`、`recap`。（`findspot` 也中 —— 正則 `\/(spot|…)` 要求斜線後
緊接 `spot`，而 `/findspot` 的斜線後面是 `f`。用子字串做黑名單本身就脆。）

這**不是**先前那兩次的家族：不是 SW 版本混搭（`app.js` 缺路由），也不是
`notFound` 的 fallback —— 是**自己把自己踢走**：在某一頁寫入資料，觸發了另一頁
留下來的訂閱，那一頁就把當下的畫面畫掉了。

### 修法

黑名單在這裡註定會漏（每加一個子頁就要記得回來補一行，漏掉的後果是「使用者在
那一頁做任何會寫入的事，畫面就被抽掉」）。改成問一個不會漏的問題：

```js
function onTripPage(tripId) {
```

## v1.73.3 五個「改壞了也不會紅」的假斷言

健檢代理實測示範了「把程式碼改壞、測試照樣全綠」。這一版把它們一個一個修掉，

`js/views/recap.js` 的 `block()` 只記 `{ name, y0, y1 }` —— **完全沒有 x 座標**。

那正是 v1.59 實機踩到的「按了天氣被踢回首頁」。

擴大之後當場誤報了一個 `spot` —— 查證是**我的比對錯**（`/trip/:id/spot/:spotId` 是兩段式
路由，比對要求段名後緊接引號），不是真的缺路由。修掉後兩步突變都會紅。

### ④ `updatetest` 有兩條 catch 的退路值恰好等於通過條件

```js
const tabAAfter = await tabA.evaluate(…).catch(() => ({ build: 'E', bar: false }));
if (tabAAfter.build === 'E' || tabAAfter.bar) ok(…)
```

`VERSION = 'E'` 是新版本號，所以 `build === 'E'` ＝「換好了」。分頁重載中 `evaluate`
丟「Execution context was destroyed」是家常便飯 —— 這條斷言**不可能失敗**。
這是偽**通過**，比偽失敗危險。

但也不能反過來把例外當失敗：例外正是因為分頁在重載，而重載就是成功的樣子。
改成**重試讀取**（等重載完再讀一次，拿真實狀態判），另一條的退路字串也改成誠實地

### ⑤ `scrolltest`「用平滑捲動」約 1/3 機率偽失敗

它靠數**瀏覽器的 scroll 事件**分辨動畫與一步到位，而註解自己就寫著「瀏覽器會合併
scroll 事件」。單獨跑三次得到 **5／3／1** 次取樣，門檻 `>= 3` 正好卡在雜訊上。

查下去發現真正的原因不只是事件合併：`smoothScrollTo` 在**開頁的忙碌期**被呼叫，
第一個 `requestAnimationFrame` 常常已經超過 320ms 的動畫長度，`p` 直接等於 1、
**動畫塌成單幀**。也就是「開行程頁時的自動捲動」在 headless 環境根本觀察不到動畫過程。
（加上 `--disable-renderer-backgrounding` 那組參數仍然如此。）

拆成兩件事各自驗：「有捲到今天、停在正確位置」用原本的行為斷言（穩定）；
「捲動是平滑的不是硬跳」改成在頁面**靜下來之後直接呼叫** `smoothScrollTo` 並數
**App 自己的 `window.scrollTo` 呼叫**（不是瀏覽器的 scroll 事件）。
判準是「連續快速呼叫的最長一串」——rAF 的幀間距 ~16ms，而各自獨立的單次捲動
（例如 router 導航那一次）差上百毫秒。實測平滑 **15／12／6 幀、跨 ~330ms**
（對得上 `dur = 320`），reduce-motion **1 幀**。判別空間從 3:1 變成 10:1。

### ⑥ `photosynctest` 斷言單一次 drain 的計數（競態）

`yes(t1.uploaded === 3 && t1.failed === 3, ...)` —— 但背景自動 drain 可能先跑掉
一部分，機器忙的時候實測會變成 2/2 或 1/1。這一次它讓整輪完整 `npm test` 白跑一次，
而我一開始以為是同步程式碼的回歸 —— 實際上是我自己測試留下的 6 個 `workerd`、
12 個 node、18 個 headless chrome 在吼背景（清掉之後連跑兩次 20/20）。

修法：drain 到佇列裡沒有還能送的東西為止，把計數**累加**起來再判 ——
量的是「這 6 個 blob 最後各自的下場」，不是「剛好這一輪跑到幾個」。
實測：同時跑兩支別的測試製造負載，照樣過。

## v1.73.2 合併層對「比自己新的欄位組」要誠實（三代理投票 2:1）

### 使用者現象

媽媽的手機停在舊版，她只是改了個行程名，爸爸設好的「每天幾點出發」就跳回舊的；
爸爸再改一次，媽媽下次改任何東西又跳回去，**來回不會停**。

### 根因是兩段，不是一段

1. 舊版客戶端的 `mergeRecord()` 用**它自己那一版的 `TRACKED`** 重建 `_f`，
   不認識的欄位組（v1.69 才加的 `trip.dayStarts`）整個消失 —— 但值跟著
   `{...base}` 活了下來。
2. 新版節點再讀這筆時，`effTs()` 找不到 `_f.dayStarts` → **退路到 `updatedAt`**
   → 那個舊值取得一個全新的時間戳，於是贏過正確的新值。

第 1 段永遠修不掉（做這件事的是使用者手機上那台舊版）。**第 2 段完全在我們手上，
而且是誤判。**

### 為什麼修得到（這一點三個代理意見分歧，我自己實測定案）

有一票投「不修」，理由是「剝除發生在舊版那台，舊版不會有修正」。**這個前提是錯的：
每一筆記錄都要過 Worker 的 `handlePush` → `mergeRecord`，那個判決才是寫進 D1 的。
伺服器是唯一的必經關卡，也就是仲裁者。** 我用真的 `js/merge.js`（只把 `TRACKED`
裡的 `dayStarts` 用字串手術刪掉當舊版）做三節點重現：

| 部署範圍 | 伺服器上的出發時刻 |
|---|---|
| 現況（都沒修） | ✗ 9:00（被舊值蓋回） |
| **只有伺服器修好，客戶端完全不動** | **✓ 7:00** |

所以**部署順序是 Worker 先、客戶端後**，而且中間的空窗期是最安全的狀態。
反過來（客戶端先）會造成永久分歧：舊 Worker 的 `sanitizeF` 會砍掉新鍵，
新客戶端把它讀成「沒有意見」，兩台新裝置各守各的值、誰也贏不了誰。

### 改了什麼（`js/merge.js`，四處）

**戊 —— `effTs` 分辨兩種「沒有 `_f[g]`」**
`store.js` 的 `put()`／`patch()` 都走 `seedF`，`seedF` 會把「自己認得的組」補齊；
`mergeRecord` 也是重建全部認得的組。所以「`_f` 非空卻缺 `g`」的**唯一**成因就是
「寫這筆的那一版不認得 `g`」—— 它對 `g` 沒有意見，不能拿 `updatedAt` 冒充。
`_f` 完全沒有的（v1.55 以前的記錄）維持原本的 `updatedAt` 退路。

**甲′ —— 未知 `_f` 鍵原封帶過去，而且只從 `base` 那一側帶**
不是取兩邊 `max`。未知欄位的「值」本來就是 `{...base}` 抄來的，時間戳從同一筆抄，
值與時間戳才配得起來。取 `max` 會讓舊值配到一個**貨真價實**的新時間戳 —— 那比
丟掉還糟：丟掉 `effTs` 偵測得出來，錯配偵測不出來。

**`seedF` —— 只播種真正的舊記錄**
`_f` 已經非空的話，缺席的組不該用現在的時間戳補 —— 那等於幫一個抄來的舊值蓋新章。

**`sanitizeF` —— 未知鍵放行，但加三道閘門**
放行是為了讓伺服器變成透明管道（以後再加新欄位組就不必再遵守部署順序）。
閘門：未知鍵最多 8 個、鍵名 `^[A-Za-z][A-Za-z0-9]{0,23}$`、值必須在
`(0, now + 26 小時]`。**值域檢查對已知鍵一併套用** —— 順手補一個既有漏洞：
以前只驗 `Number.isFinite`，所以任何客戶端推一筆 `_f: { title: 9e15 }`，
這趟的行程名就**永久凍結、誰都改不動**，介面上還完全看不出為什麼。

## v1.73.1 不會消失、不會漏算（第四輪健檢第一批）

### 會讓照片永久消失的那一條

v1.64 那條「4xx 無限重試且使用者永遠看不到」只落地了**前半**（標 `dead`、不再排程）。
後半（讓使用者看到）寫好了 `deadCount()` 就沒接上去 —— **全專案零個呼叫端**。
而三個計數器對 `dead` 的處理互相矛盾，方向還相反：

| 位置 | 以前 | 後果 |
|---|---|---|
| `syncStatus()` 行程頁進度列 | **含** dead | 「正在上傳照片… 還有 1 張」**永遠不會消失** |
| `pendingCount()` 設定頁 | **含** dead | 待送數字永遠掛著 |
| `pendingOf()` 移除旅程守衛 | **不含** dead | **守衛放行** → 只存在這台的照片被硬刪、永久消失 |

完整失效鏈：一張 413（超過 15MB）或 403 的照片 → `dead` → 行程頁永遠顯示「正在上傳」→
使用者按「移除旅程」→ 守衛不擋 → 照片沒了。而擋門的文案寫的是
「請連上網路，等行程頁的『正在傳照片』跑完再移除」—— 一個他**永遠無法滿足**的指示。

**修法**：三個計數器統一（進行中不含 dead，dead 分開報）；`deadWhy()` 把 `blob 413`
翻成「照片檔案太大，伺服器不收」；行程頁改顯示「⚠️ 有 N 張照片傳不出去（原因）——
這幾張只存在這支手機，移除旅程前請先匯出完整備份」；移除守衛對 dead 用另一句
**他做得到**的話，並提供「先去匯出」的出口。

### 兩條會讓編輯憑空消失的

- **推送途中的編輯**：`pushChunks` 在**開始時**把記錄快照下來，慢網路上一輪可以跑好幾分鐘。
  這段期間的編輯排不進 outbox（`enqueuePush` 撞到在途項目就 `return`），推送成功後那個項目
  又被刪掉 → **那些編輯永遠不會同步出去**。改成標記 `dirty`，推完依旗標決定刪還是留。
- **死掉的 `push` 項目會讓那個群組再也不同步**：`enqueuePush` 撞到 dead 項目一樣 `return`，
  而 `drainOnce` 的收尾又跳過 dead。`permanent()` 的意思是「這一個請求再送也一樣」，
  不是「這個群組沒救了」—— 內容變了就該再試。改成使用者一編輯就復活。

### 記帳漏算（兩個代理各自實測到）

`addUsage` / `addMapsCalls` 是「讀 → await → 改 → 寫」。`album.js:331` 與
`poster/index.js:456` 兩處都是 `Promise.all` 同時跑兩支 `ensure*` —— 相簿頁與海報頁
各有一個兩路並發，其中一次的花費**完全不入帳**。實測：兩路漏一半、五路漏 80%。

修法不是加鎖，是 `db.tripSecretUpdate(tripId, fn)`：把讀改寫放進**同一個** IndexedDB
readwrite 交易。IndexedDB 對同一個 store 的 readwrite 交易是序列化的，所以這樣**連跨分頁都安全**。
（`fn` 必須同步 —— 中間 await 會讓交易自動提交。）實測 2/2、5/5、5/5，零漏算。

`js/ai.js` 寫 `'claude-sonnet-5': { in: 3, out: 15 }`。**$3/$15 是原本排定
2026-09-01 生效的漲價，後來取消了**，標準價維持 $2/$10（2026-09 查證官方定價頁）。

- **但相簿／影片頁與海報頁什麼都沒說** —— 而使用者正是在那兩頁看到舊文字的

**修法**：`showAiStaleNote(tripId)` —— 文案不是最新時，在那一頁最上面加一行低調的說明
（不是紅色警告，這不是錯誤，是「為什麼沒更新」的解釋）：

> ℹ️ 這趟的 AI 額度用完了，文案沿用上一版。　[調整上限]

五種原因共用 `ai-config.js` 的 `AI_WHY` 對照表（`trip.js` 的狀態列也用同一份 ——
兩邊講的話不一樣的話使用者會更困惑），按鈕導到旅程設定。

**使用者的處理流程（已實測可行）：**
1. 旅程設定 →「進階：自帶金鑰（可選）」→「AI 加值」卡看到「已用 $X / 上限 $2.00」與進度條
2. 按「調整上限」改成更大的數字
3. 回到上面的「影片與海報文案」列按「重新產生」
   （測試驗過：`capUsd` 調高後 `canRegenerate` 立刻變 `true`、狀態從 `cap` 變 `pending`）

`aitest` 新增 4 項：額度用完時舊文案原封不動且狀態說得出原因、畫面上看得到原因與出口、
調高上限後真的能重產、沒開 AI 的行程不會亂跳提示。

## v1.72.0 中文文案的語感（使用者回報影片字卡讀不通）

**回報的句子**：回憶影片第 3 天字卡「溫泉公園漫步，品嚐在地雞湯，了解水產養殖，
溫暖的宜蘭說不再見」。最後那句漏了介詞（要嘛「向溫暖的宜蘭說再見」、要嘛
「不跟溫暖的宜蘭說再見」），整句是新聞標題式的壓縮。

**來源查明：是 AI 產的，不是句型庫。** 字卡文字走 `memory.js` 的
`aiTx.narration[day] || aiTx.dayLines[day]`，兩個都出自 `aicontent.js` 的 `ensureTripText`。
靜態句型庫（`data/phrases.json`）**全庫只有一個「說」字**，而且語法正確
（「拍一張最能說『我來過 X』的照片」）——完全沒有「再見／道別」這類需要介詞的句型。
那筆文字存成 `aiText` 記錄（`key: 'tripText'`），**帶 groupId、會同步給整個群組**，
並用 `sig`（行程內容的雜湊）快取 —— 所以行程沒改就永遠吃舊的那一份。

**根因有兩半：**

1. **提示詞把模型逼到壓縮。** 字卡只給 12～22 字，卻要它涵蓋那天所有景點
   （第 3 天有三個），等於每個景點五、六個字。壓到這個程度，最先被犧牲的就是介詞、
   助詞這些「不影響意思但影響通順」的字。原本的系統提示只寫「親切自然」—— 太抽象，
   模型接不住。
2. **模型是 Haiku。** `js/ai.js` 的 `MODEL` 是 `claude-haiku-4-5`。小模型在壓縮壓力下
   更容易掉字。

**修法：**

- 五支提示詞共用一段 `ZH_STYLE`，直接點名要避免什麼，並給**反例／正例對照**
  （抽象的形容詞沒用，對照的例子才有用）：介詞助詞不能為了省字砍掉、不要新聞標題式
  壓縮、不要流水帳、**字數是參考，寧可少寫也不要把句子壓壞**。
- 字卡那一段從源頭拆掉壓縮壓力：明講「**挑那天最有感覺的一件事來寫就好，不要把景點
  一個一個列出來**」。
- **模型換成 Sonnet 5**。實算：五支呼叫、一年 4–6 趟，Haiku $0.12／年 →
  Sonnet $0.24／年，**差 $0.12**；單趟 $0.02–$0.04
  （實量：輸入約 3,200 token、輸出上限 3,500），只用掉預設 $2 上限的 1–2%。
  這些句子是家人真的會讀到的東西，為了省一年兩毛錢讓句子讀不通不划算。
  要換回去只改 `js/ai.js` 的 `MODEL` 一行，費率表會自己跟著對。
- **舊文案怎麼辦：兩條路都給。**
  （a）新增 `PROMPT_V` 常數並**放進每一支的 `sig`** —— 改了提示詞，既有行程在建立者
  下次開啟時會自動重產一份。不進 `sig` 的話，改提示詞對既有行程完全沒有效果。
  （b）旅程設定多一列「文案讀起來怪怪的 → 重新產生」（`clearTripText`），把五種
  `aiText` 記錄清掉、並把景點介紹換回內建版。**這會同步給旅伴** —— 這是對的，
  大家看的本來就該是同一份文案。

**順帶抓到一個靜態句型庫的真 bug**（`composeBlurb`）：食物主題有 4／12 句需要 `{must}`
（必吃項）。原本的寫法是「挑到了再重抽，最多四次」，四次都抽到就落到退路
`b.blurb[0]` —— 而食物主題的第一句正好就是「來{name}就是要吃{must}，記得留點胃口。」，
`{must}` 被替換成空字串就變成「來羅東夜市就是要吃，記得留點胃口。」。改成用 `pick()`
本來就支援的 `allow` 條件**從源頭排除**，退路也不再用 `blurb[0]`。實測 500 次 0 壞句，
有必吃項時 73/200 照樣用得到 `{must}` 句型（沒有被過度過濾）。

**新測試 `npm run zhtest`（15→17 項）**：
- 靜態句型庫 **924 句全部展開**（不是抽樣）跑語法紅旗
- **對照組**：把使用者回報的那句丟進檢查器，確認抓得到 —— 不然這就是個永遠會通過的
  空檢查器。（第一版的「說再見缺介詞」規則用 lookbehind 寫，會誤殺正確的
  「向溫暖的宜蘭說再見」；改成看整個子句有沒有介詞。）
- `composeBlurb` 沒有必吃項時不吐半截句子
- 五支提示詞都帶 `ZH_STYLE`、`PROMPT_V` 進了每一支的 `sig`、有重產的路、模型是 Sonnet 5

**能驗與不能驗**：AI 的輸出沒辦法在測試裡驗（那要真的打 API，需要使用者的金鑰）。
測試能守的是「提示詞有沒有把話講清楚」與「靜態的那一半有沒有問題」。

## v1.70.1 對抗性複查（使用者要求把 effort 調到 Max 之後的第一件事）

v1.66–v1.70 是連續四版快速出貨的，所以回頭做了一次逐行複查。抓到五個問題，每一個都
先寫出可重現的證據才動手，五個都補了回歸斷言：

1. **Google 額度會少算**（`views/nearby.js`）。`addMapsCalls` 寫在「作廢檢查」後面：
   使用者在等待中途換分類，那次呼叫已經送到 Google 了卻沒被記到。這個計數器是花費
   保險絲，漏記就是把保險絲弄鬆。改成**先記帳再看結果作不作廢**。
2. **半小時時區偏移解析錯誤**（`transit.js`）。原本 `parseInt(iso.slice(-6,-3))`，
   `+05:30` 被讀成 `5` → 整批發車時刻差 30 分鐘。這條路徑不是理論的：`tzOffsetFor`
   認不出地點時會退回**本機時區**，人在印度出差時規劃日本行程就會走到。
3. **Google 請求沒有逾時**（`transit.js`／`places.js`）。`signal` 是選配參數而兩個呼叫端
   都沒傳 —— 對方掛住，畫面上那顆按鈕就永遠停在「查詢中…」。補上預設逾時
   （Routes 15 秒、Places 12 秒，跟 Overpass 同一套 `AbortSignal.timeout` 寫法），
   實測 15 秒放棄並回 `timeout`。
4. **連續套用時，前一條「已解決」會被蓋掉**（`views/plan.js`）。`paint([{...}])` 每次
   只帶一條，第二次套用時第一條就無聲消失了 —— 這正好違反代理明確要求的「已解決的
   原地變成 ✓，不無聲消失」。改成累積，而且**每一列各自帶自己的復原快照**（按鈕長在
   那一列上，一顆「復原」就不該把前面幾條一起倒回去）。
5. **「排到隔天」可能整個建立在我們自己猜的停留上**（`plancheck.js`，代理 C 點名過、
   我當初漏了）。實測：使用者只填了「夜市 22:00」一個時間、後面兩站什麼都沒填，我們
   照樣宣稱「這一天會排到隔天 02:10」—— 那個 02:10 是三個猜出來的停留堆出來的。
   不刪掉這一條（「你這天比想像中長」是有用的訊息），但**要講清楚它是推算**：
   有假設停留時改寫成「照目前的推算，這一天會排到隔天 02:10」＋「有幾站的停留時間是估的」。

順帶修掉兩個**測試本身**的問題：`checktest` 原本會打到真的
`routing.openstreetmap.de`（實測被回 429，既慢又不決定性，還占用公共服務）→ 改用假
OSRM；「旅伴同時在改」那一條原本在「按鈕根本不存在」時會**空轉通過**，補上前置斷言。

## 停車場雙軌（v1.70，Google 為選配）

`js/places.js` + 「找附近 → 停車場」的「🔍 用 Google 再查一次」。**OSM 仍然是預設。**

為什麼是雙軌而不是換掉：
- **Places 的內容不准長期儲存**（除了 `place_id`）。要換成 Google 就得拿掉現在的一天快取，
  也就是開車到訊號不好的地方就查不到停車場 —— 對「找附近」是明確的退步。
- 沒有金鑰的人不能因此變差（免費路徑不能退化）。
- 鄉下的 OSM 常常比 Google 全：Google 收的是**營業場所**，路邊的公有停車格不一定在。

Google 的強項是 `businessStatus`（歇業的直接不列，OSM 沒有等價欄位）與營業場所的名稱。
按下去才會發請求；每一張卡標「Google」（條款要求標示出處）；畫面明說這份資料不會存進手機、
離線時看不到，並且提供「↩︎ 回到地圖資料（可離線）」。

FieldMask 刻意只要 `id`／`displayName`／`location`／`businessStatus`／`shortFormattedAddress`
—— **`rating` 與 `userRatingCount` 會把整個請求升到 Enterprise 級計費**，不要。

## 行程檢查與逐條套用（v1.69）

`js/plancheck.js` + 調整行程頁每一天的「⚠️ 檢查（N）」。三個 Opus 5 代理 3:0「GO with changes」，
Q1 一致選 **(B) 推算出來的時刻不寫進資料**。

**為什麼不寫（否決另外兩個方案的理由，兩個都是我沒想到的）：**
- 否決「加 `timePinned` 旗標」：`merge.js` 的欄位組只搬「自己那份欄位清單裡的欄位」。**舊版
  App 的 `TRACKED.spot.time` 清單裡沒有新旗標**，所以在舊版手上 `startMin` 走時段組的勝方、
  旗標卻跟著整筆 LWW 的勝方 —— 機器算出來的時間會被標記成「使用者親手鎖的」，正是要避免
  的半套狀態，而且新版客戶端修不掉。混版在這個專案是常態不是例外。
- 否決「加 `autoMin` 欄位」：推算值**每台裝置不一樣**（`travelMatrix` 拿到 OSRM 就用真實路網，
  離線／429／逾時就降級成直線估算）。兩台各自寫進去、互相推播、拉下來再重算再寫 ——
  **永不停止的同步雜訊**，而 v1.65 才剛為 579 筆／264 KB 做了分塊上傳。
- (B) 的成本是零：不新增欄位、不動 `TRACKED.spot`、既有讀取點 0 處要改。而且 `plannertest.mjs`
  早就有一條釘住的斷言「沒動『幾點到』→ 存進去是空的」——(B) 就是把這條不變量延續下去。

**唯一新增的欄位是 `trip.dayStarts`**（每一天幾點出發，自成一組）。它是使用者自己設的、不是
推導值，所以進同步層完全正當。沒有它，`chainTimes` 在「當天沒有任何景點填時間」時整條鏈
回傳 null —— 而那正是自動排時刻表最主要的情境。**加了新欄位組 → Worker 要重新部署**
（`sanitizeF` 會把不在白名單裡的 `_f` 鍵刪掉）。

**偵測規則的最終清單**（原提案三條被換掉兩條、補上一條）：

| 規則 | 輸入 | 呈現 |
|---|---|---|
| `order` 使用者填的兩個「幾點到」前後顛倒 | 純使用者輸入，零估算 | ⚠ 警告，建議**對調順序** |
| `overlap` 前一站的固定時段還沒結束下一站就開始 | 同上 | ⚠ 警告，建議**縮短前一站停留** |
| `late` 趕不上 | 含估算 → 三道閘 | ⚠ 警告，建議縮短前一站停留 |
| `overnight` 這一天排到隔天 | 純算術 | **陳述不是警告**（夜景→夜市→凌晨拉麵是正當安排） |
| ~~到達時已打烊~~ | **沒有資料源** | 刪除，見下方待辦區 |

- `order`／`overlap` 這兩條是三個代理**各自獨立提出並都排第一**的，因為完全不需要估算。
  實務命中率不低 —— 拖拉重排與「排順序」只改 `day`/`order`、**完全不碰 `startMin`**。
- **連鎖項目收斂回根因**：同一站已經因為 conflict 被報了就不再報 late（否則兩條的修正建議
  互相矛盾：一個要對調順序、一個要縮短停留）。
- **修正一律優先動 `stayMin` / `order`，不新增 `startMin`** —— 幫景點補上 `startMin` 等於替
  使用者種下一個永久的固定時刻約束，從此每次微調順序都會跳警告。這是代理點名的阻斷級問題。

**互動（代理找出的兩個阻斷級漏洞都補了）：**
- **每套用一條就重新偵測**（鏈式問題：修第一條後面的建議值就過期了）。成本是零 ——
  `chainTimes` 是純函式，`travelMatrix` 的 `canonical()` 保證重排不觸發新的 OSRM 請求。
  但存活的項目**不重新排序、不重新編號**，已解決的原地變成「✓ 已改好」不無聲消失。
- **套用當下重讀記錄比對**。`plan.js` 原本**沒有訂閱 store**（`sos.js`／`trip.js` 有），而前景
  每 20 秒 pull 一次 —— 旅伴的修改進了 IndexedDB 但畫面不動，按下去就會用預覽時算的舊值
  蓋掉他。現在比對 `updatedAt`，不符就不寫、改成重新檢查並說明。順帶補上 `store.subscribe`。
- 功能內復原（記憶體快照，不建通用 undo）。復原本身是一次新的 patch，時間戳更晚，所以
  跨裝置會正確收斂，不需要特殊機制。
- 「這樣沒關係」寫 `_ok` 本機旗標（`_` 開頭不觸發同步）**並帶簽章** —— 之後改了時間，
  問題會重新出現，不是永久消音。
- 一次最多 3 條，**依當天時間先後排不依嚴重度**（三個代理都明確反對嚴重度排序：長輩是
  照順序讀行程的，而且修最早的通常會連帶解掉後面的）。
- 沒有「全部套用」：它在依賴性下沒有正確語意（要嘛拿過期的建議一次寫下去，要嘛做成一個
  會震盪的小型求解器）。一年 4–6 趟、典型 1–3 條，逐條按的成本本來就很低。

## 大眾運輸時間（v1.68，需自帶 Google 金鑰）

`js/transit.js` + 旅程設定的「地圖加值」卡 + 調整行程頁每一天的「🚆 大眾運輸」按鈕。

- **為什麼是「按一下才算」不是背景自動跑**：大眾運輸的答案取決於幾點出發，而第 n+1 段的
  出發時間要等第 n 段查完才知道。所以只能**一段一段序列查**（4 個景點＝3 次請求，19 個
  景點約 5–6 秒），不能像開車估算那樣一次拿整張矩陣。順帶一提 `computeRouteMatrix` 的
  TRANSIT 模式**上限只有 100 個元素**（一般模式 625），就算不管時間問題也塞不下。
- **時區是必要的一環**：`startMin` 是「當地牆上時鐘」沒有帶時區，但 Routes API 的
  `departureTime` 一定要絕對時間 —— 差一小時查到的班次就是錯的。用旅程的 `country`
  （建立行程時選的 TW/JP/KR）為主、座標框為輔，都對不上才退回本機時區**並在畫面上標明
  「時間可能差幾小時」**，不默默給錯答案。
- **顯示上要分得出「實際班次」與「估算」**：大眾運輸給底色、正常字級，列出路線名／上下車站／
  發車時刻／轉乘次數／走路時間；開車估算降級成灰色附註。
- **沒有金鑰時完全維持現狀**：按鈕不出現（不給看得到按不了的東西）、開車估算照常、
  **零個 Google 請求**（transittest 有斷言）。
- **用量算次數不算錢**：Google 的免費額度是「每月幾千次呼叫」，換算成美金永遠顯示 $0，
  對使用者沒有意義。預設上限 300 次／月，這是**保險絲不是預算**（迴圈寫錯一次就可能燒掉額度）。
- 快取在 IndexedDB，key ＝起訖座標＋星期幾＋出發的半小時區間，TTL 24 小時。
- 金鑰跟 AI 金鑰**分開**（`tripSecrets` 的 `mapsKey`），也**獨立於 AI 開關** —— 想查班次的人
  不一定想開 AI 加值。同樣絕不同步、絕不匯出。
- FieldMask 只要必要欄位；評分／人氣／路線圖形都不要（那些是更貴的計費等級）。

## 時刻鏈修正與行程檢查（v1.67）

三個 Opus 5 代理評估「行程安排最佳化」時各自獨立指出、我逐一餵資料重現的**現行錯誤**（Fable
額度用盡，這一輪改用 Opus 5，屬例外；慣例仍是 Fable 5.1——當時的模型設定）：

- **跨區之後會瞬間移動**（`route.js` 的 `chainTimes`）。原本 `cur = leave != null ? leave : cur`，
  跨區段的 `leave` 是 `null`，於是 `cur` 停在跨區前那一站的離開時間，下一站從那裡繼續往下加。
  實測：台北 09:00 停 60 分 → 飛沖繩（停 60 分）→ 沖繩隔壁站，第三站算出「**10:05 到**」——
  飛行時間與沖繩那一站的停留都憑空消失。現在跨區之後鏈中斷（除非下一站自己填了「幾點到」）。
- **跨午夜會報出荒謬的遲到**。使用者填的「幾點到」是牆上時鐘（`minOfInput` 上限 1439），推算到達
  卻可能已經跨日。實測 23:00 夜市停 90 分 → 01:00 宵夜，`late=1413`，畫面會寫「⚠ 比預定晚
  **23 小時 33 分**」。現在先把固定時刻平移到離推算值最近的那一天再比（`alignDay`）。
- **只有舊字串時間的記錄對時刻鏈完全隱形**。`spottime.js` 開頭寫著「所有要顯示時間的地方都走
  這裡」，但 `chainTimes` 當初直接讀 `s.startMin`。實測 `startTime:'09:00'` 的舊記錄 `fixed=false`、
  `arrive=null`，**整條鏈跟著全空**。現在走 `spotTimes()`。

以及兩項新的：

- **停留時間依景點類別推**（`theme.js` 的 `stayForSpot`，資料在 `data/themes.json`）。原本沒填停留
  一律當 60 分。現在 11 個主題各一個值（夜市 90、遊樂園 240、判斷不出類別的維持 60「不裝懂」），
  外加名稱層級覆寫處理「同類別差十倍」的情況（`transit` 同時涵蓋機場 120 分與捷運站 20 分）。
  畫面照樣標「（停留未設，先用 1 小時 30 分推算）」，把主觀判斷從警告降級成**可以直接改掉的預設值**。
  三代理 3:0 決議用對照表而非 AI 推估，決定性理由是**同步一致性**：AI 金鑰只存在建立者那一台
  （`tripSecrets`，絕不同步），走 AI 會讓同一個景點在爸爸手機顯示「建議 2 小時」、媽媽手機顯示別的。
- **「使用者自己填的時間互相矛盾」偵測**（`route.js` 的 `timeConflicts`）。三個代理各自獨立提出
  這一條並都排第一，因為它**完全不需要估算**：不看車程、不看假設停留、不受跨區中斷影響，純粹是
  使用者親手輸入的兩個數字打架。實務命中率不低——拖拉重排與「排順序」只改 `day`/`order`、**完全
  不碰 `startMin`**，所以「把訂了 13:00 的餐廳拖到 15:00 的景點後面」是家常便飯，而原本 App 一聲不吭。
  唯一的誤報來源是跨午夜（23:00 夜市 → 01:00 宵夜），所以「晚上 18:00 後 → 凌晨 06:00 前」這一組
  直接跳過不判——**刻意選擇漏報而不是誤報**，誤報一次長輩以後就不看了。
- **遲到警告分軟硬**（`lateSoft`）。這個數字的輸入有兩個常常是猜的：車程在離線時是直線 ×1.4、
  上一站的停留可能是我們自己填的預設值。所以只有「矩陣來自 OSRM ＋ 上游沒有任何假設停留 ＋
  遲到超過 20 分」才寫「⚠ 比預定晚 X」並標紅；其餘降級成灰字「可能有點趕（推算晚 X，含估算）」。

## 同步分塊與限流（v1.65）

- **日常同步改分塊推送**（`js/outbox.js` 的 `pushChunks`）：以前是「一個 POST 送全部」，真實家族群組已經是 **579 筆／264 KB**，逾時 15 秒。慢網路實測（上行 60 kbps／延遲 400ms）：**改善前整包 15 秒逾時失敗；改善後 157 秒內 579/579 全部送達**。斷線續傳：進度（送到第幾筆）記在 outbox 項目上，**全部批次成功才刪項目**；實測斷線時記到第 80 筆，恢復連線後 1.7 秒補完。只有在「記錄清單沒變」（筆數＋頭尾 id 當簽章）時才續傳，免得中間插入新記錄造成位移跳號。
- **Worker 限流**（`workers/worker.mjs` 的 `limited()`）：額度 上傳 200／分、push 30／分、resolve 5／10 秒、建新群組 3／分。**key 用群組祕鑰的雜湊**（一家人同一個 Wi-Fi，用 IP 會把全家算成一個人）；但**建新群組只能用 IP**——那時候祕鑰是請求方自己指定的，拿它當 key 等於沒擋。
  - **實作用 D1 計數，不用 Cloudflare 的 Rate Limiting 綁定**：實測那個綁定在這個帳號/方案上**完全不計數**（連續 40 次以上呼叫、額度設 5／10 秒，每次都回 `success: true`），官方文件也自承它「不是精確的計數系統」。WAF 的 rate limiting 規則則對 `workers.dev` 不適用（需要把網域加進 Cloudflare 當 zone）。
  - 線上實測：`/resolve` 第 6 次起 429、建新群組第 4 次起 429。
  - 378 個檔案（189 張照片）的爆量實測全部送達、一個都沒卡住；真機速率約 150–400／分，額度 200／分約 2 分鐘傳完，不會擋到自己人。
  - 已知限制：攻擊者換 IP 就能繞過建新群組的限制；這裡擋的是失控迴圈與掃描器，不是有心人。
  - `rl` 資料表由每日 cron 一併清掉一天以上的舊列。

## 第三輪全面健檢（v1.64.0，v1.55.1 之後）

四路稽核（程式面／外部服務／安全隱私／資料一致性＋測試品質）。**已修**：
- **LAN server 靜態檔黑名單可用大小寫繞過**（`/SERVER/data/state.json` ＝所有群組明文祕鑰＋全部記錄含座標；自架開 tunnel 等於公開在網路上）→ 改白名單。**這輪最嚴重的一個。**
- **照片上傳沒有逾時** → 一個停住的 PUT 會讓 drain 的 `Promise.all` 永不 resolve，**從那一刻起連 pull 都停了**（v1.63 剛做的即時感全失效）→ 依檔案大小給 30–180 秒逾時。
- **`refreshNow()` 帶 force** → 每次開行程頁/照片牆/SOS 頁都把整個群組（幾百筆、數百 KB）POST 上去；這是 v1.63 帶進來的退化 → 拿掉 force（pull 本來就無條件執行）。
- **4xx 無限重試且使用者永遠看不到**（祕鑰不符、檔案太大每 5 分鐘重打一次，畫面只顯示「正在上傳」）→ 標記 dead 不再排程。（**v1.73.1 更正**：「排除在待送計數外」當時只有 `pendingOf`（移除旅程的守衛）做了，而那正是**唯一不該排除**的那一個 —— 守衛因此對永久失敗的照片直接放行。真正該排除的 `syncStatus`／`pendingCount` 反而含著 dead，所以進度列永遠停在「正在上傳照片」。兩邊都錯、方向相反，v1.73.1 才真的做對。）
- **`TRACKED.trip` 漏了 allowGeo／allowWiki／aiEnabled** → 旅伴離線改行程名再同步回來，建立者開的 AI 會被靜默關掉 → 補進欄位組。
- **Worker 的 TRACKED 白名單是手抄的**（`type IN ('spot','trip','quest')`）——所有本機測試都跑 LAN server，只有正式 Worker 用這份清單，漂了測不出來 → 改成從 `TRACKED` 生成。
- **建立者補問對 v1.60 以前的行程完全不生效**（`createdByDevice` 那時還不存在，而使用者現在用的正是這種）→ 退而看「這台裝置寫過這趟的資料」。
- **位置墓碑 fire-and-forget**（註解寫「下一次 drain 會補送」，但 drain 只在有待送項時才推）→ 改成失敗就排進 outbox；`stopSharing` 等推送完成；時間戳改單調（手機校時往回跳會讓墓碑輸給座標）。
- **`expireMine()` 是死碼**——「24 小時自我清除」只有「不顯示」是真的 → 接上 `updateNow`。
- **cron 會被自己產生的墓碑塞滿**（墓碑改寫後 `updated_at` 變成當下，48 小時後又落回條件）→ 只挑還有座標的、依時間排序。
- **公開相簿的照片路徑可放 text/html**（繞過 `script-src 'none'`）→ 上傳與回傳都夾成圖片型別＋nosniff。
- **邀請連結的 `u=` 可換掉同步伺服器**（一條假連結就能把之後所有群組的資料與祕鑰導去攻擊者）→ 只收 https，非內建網址要使用者看過主機名才繼續。
- **「清除所有資料」只清 IndexedDB**（最後定位、住家座標、反查地址、位置分享開關都留著）→ 一併清 `tripquest.*`。
- **Overpass 伺服器逾時 25 秒 > 客戶端 12 秒**（我們放棄了對方還在跑，又送第二個鏡像）→ 對齊成 10 秒。
- **維基查詢失敗被寫成 30 天負面快取**（剛好那一秒慢，之後一個月都查不到）→ 失敗不寫快取。
- **測試會把群組寫進正式 D1**（發現 16 個測試群組）→ 見下方環境注意事項。

## 已知限制與未解事項

- 免費地圖資料：餐廳覆蓋 OK 但**無評分、營業時間僅一~兩成、日本店名無中文**；「值得去嗎」答不了。

## 環境與帳號注意事項

- **日期一律先跑 `date`，不要從對話推、也不要照抄別人的文件**（2026-09-19 實測：統籌者的規格把今天寫成 09-20，
  我照抄進 STATUS 兩處；回報的「距上次全面檢測」也手寫成 2 天）。回報最後那行一律貼 `npm run affected` 印出來的。

- **推送閘**（2026-09-23）：推送一律 `bash scripts/safe-push.sh`（或 `npm run safepush`），不要自己 `git push`。
  它依序做：① `scripts/prepush-scan.mjs` 掃**遠端還沒有的每一個 commit** 的新增行（金鑰或 token、email、本機使用者名稱、
  磁碟機或家目錄路徑；每一類先在合成樣本上命中）→ ② `git push` → ③ 比對遠端 main ＝ 本機 HEAD。回傳值：0 已推送；
  1 自查有命中；4 自查的檢查器壞了；2 push 失敗；3 推了卻沒更新——一看就知道是哪一關。它抓不到個資，**新增的文件行
  還是要自己看一遍**（共用慣例附錄 A）。新 Session 不需要準備任何東西：使用者名稱是執行當下從環境變數讀的，
  email 的對照組是當場組的合成字串，腳本裡沒有不能公開的樣式或黑名單。
  **為什麼長這樣**（今天四個 App 各踩一次的同一類坑）：推送流程原本是「跑自查、看輸出、另外推」，擋的是人眼；
  接成一行後又用 `| tail -1` 截輸出——管線的回傳值是最後一個指令的，本 App 實測 `git push` 失敗時照樣回 0，後面的
  線上確認會對著舊版驗、看起來還是綠的。原本只看 HEAD 一個 commit，一次推兩個時前一個沒被掃。原本放在 Session
  的暫存區，換 Session 就沒有防線。以上都由 `pushgatetest`（在鏈裡）守著。
