## 一句話

把「每版 `npm test`（43 支）全綠才能 push」改成「每版跑**底線＋受影響的測試**，全面檢測由 Yolin 指定」；「受影響」不靠人判斷，由一支新的純函式挑選器 `scripts/affected.mjs` 依 git diff 算出來，而且這支挑選器要先通過本 App 七個歷史案例的回放。

## 2. 目標與非目標

**目標**：G1 平常一版的測試時間明顯下降；G2「受影響」由工具算、不靠人讀表；G3 歷史上七個波及案例，新流程每一個都還抓得到；G4 回報裡永遠看得出這次跑了幾支、不是全綠；G5 Yolin 隨時看得到距離上次全面檢測多久了。

**非目標**：不引入突變測試工具、不做 CI、不重構任何既有測試、不改任何 `js/`／`css/`／`workers/`／`server/`／`sw.js`、不為了量秒數專程跑一次全套、不動 `CLAUDE.md` 檔尾的「共用慣例」指向段、不動 `docs/CONVENTIONS.md`。

## 3. 名詞

| 名詞 | 意思 |
|---|---|
| 鏈 | `package.json` 的 `test` script 用 `&&` 串起來的那一串（現在 43 支） |
| 底線 | 不論改了什麼，每版都跑的一小組便宜測試（R2） |
| 直接引用 | 某支測試腳本的文字裡出現了某個 repo 內的檔案路徑（含 `page.evaluate` 裡的動態 import、`spawn` 的伺服器、fixture） |
| 閉包 | 一個 `js/` 檔沿著靜態 `import` 往下展開到的所有 `js/` 檔 |
| 放大器 | 改到特定檔案時，強制加跑一組測試或直接跑全套的寫死規則（R4） |
| 全面檢測 | Yolin 指定才跑：完整 `npm test`＋`npm run sweep`（R6） |

## 4. 規則

- **R1 每版要跑的＝底線 ∪ 挑選器算出來的測試。** 指令是 `npm run test:affected`（新增）。它先印出清單與理由，再**依鏈的順序、一次一支**跑（不平行——這個 repo 的測試會互相搶資源）。任何一支紅就停。
- **R2 底線（每版必跑）**：`validate-places`、`zhtest`（純 Node，幾乎零成本）、`nearbytest`（路由表與 SW SHELL 的完整性稽核）、`emptytest`（view 原始碼守衛）、`tabbartest`（案例 ① 的受害者，守每一頁的骨架高度）、`affectedtest`（新增，守挑選器自己）。部署後的 `npm run sweep` 照舊每版必跑——少跑全測之後，它是唯一的橫向掃描，地位更重要。
- **R3 挑選（`scripts/affected.mjs`，純函式，不讀 git、不跑測試，方便單元測試）**：輸入＝改動的檔案清單＋鏈裡每支測試的腳本文字＋`js/` 的 import 圖。一支測試被挑中，條件是下列任一：
  1. 這支測試的腳本檔本身被改到；
  2. 它直接引用的某個檔被改到（`js/`、`css/`、`workers/`、`server/`、`data/`、`scripts/fixtures/`、`sw.js`、`index.html`）；
  3. 它直接引用的某個 `js/` 檔的**閉包**裡有檔被改到（例：測試引用 `js/store.js`，`store.js` import `js/db.js`，改 `db.js` 就算）；
  4. 命中放大器（R4）。

  呼叫端（`scripts/run-affected.mjs` 或等價物）負責取改動清單：`git diff --name-only HEAD` ＋ `git ls-files --others --exclude-standard`（未追蹤的新檔也算）；可用參數換比較基準（例如上一個發版 commit），給「一版分好幾個 commit」時用。
- **R4 放大器（寫死在挑選器裡）**：

| 放大器 | 觸發 | 放大到 | 依據 |
|---|---|---|---|
| A 畫面結構 | 改到任何 `js/views/*.js`，或 `css/style.css` | 加跑 `layouttest`、`tabbartest`、`scrolltest`、`densitytest`、`recapcardtest`、`screenshots`、`tagtest`、`walltest` | 案例 ②③⑤⑥；唯一的全域 CSS 檔有類名撞車的前科 |
| B 資料與同步層 | 改到 `js/store.js`、`db.js`、`outbox.js`、`sync.js`、`ids.js`、`share.js`、`photos.js` | 加跑鏈裡所有會起 `server/index.mjs` 的測試（勘查時 14 支；以程式實際掃到的為準，不要寫死 14） | 案例 ⑤ 的 `synctest`；這幾個檔被 12–38 支測試引用 |
| C 骨架與合併語意 | 改到 `sw.js`、`index.html`、`js/app.js`、`js/router.js`；**新增或刪除**任何 `js/views/*.js`；改到 `js/merge.js`、`workers/**`、`server/**` | **全套**（＝完整的鏈） | 案例 ①⑦：路由層的波及無法預測；合併語意錯了會永久寫進 D1、救不回來 |
| D 沒人認領的程式檔 | 改到 `js/`、`css/`、`workers/`、`server/` 底下的檔，但**沒有任何一支測試**透過直接引用或閉包涵蓋它 | **全套**，並在輸出裡點名是哪個檔 | 挑選器壞掉或涵蓋不到的樣子，就是「少挑幾支、看起來照樣全綠」。寧可多跑 |

  只改 `docs/**`、`*.md`、`screenshots/**` → 只跑底線。只改 `package.json` 的 `test` 鏈或 npm script → 底線（`affectedtest` 會驗鏈）。
- **R5 輸出口徑**：挑選器每次都印 `這不是全綠：本次跑 N/M 支`（M＝鏈的實際長度，從 `package.json` 數，不寫死）與每支被挑中的理由（哪個檔、哪條規則）。命中 C 或 D 時印 `放大到全套` 與原因。**回報與 commit 訊息不准寫「全綠」**，要寫「底線＋受影響 N/M 支綠」；只有真的跑完整條鏈才能寫全綠。
- **R6 全面檢測**：由 Yolin 指定才跑＝完整 `npm test`＋`npm run sweep`。`livetest`（會在正式 D1 建群組）不含在內，除非 Yolin 點名。每次跑完在 STATUS「測試」節更新一行「上次全面檢測：日期、版本、結果、總耗時、最慢的五支與秒數」——**耗時就在這時候順便量**，不為了量秒數專程跑。
- **R7 提醒而不自動**：每版的回報最後加一行「距上次全面檢測：N 版／D 天」。要不要跑由 Yolin 決定，Session 不自己跑。理由：日期走過去造成的失敗（§1 第三件）git diff 挑不到，只有定期全測抓得到；Yolin 說他會定期叫，這一行只是讓他不必自己記。上次全套的基準是 v1.73.6（2026-09-18，43 支 1425 條全綠）。
- **R8 沒有放寬的部分**：新斷言仍然要證明會紅（手動把邏輯改壞或拿修正前的程式跑）；修 bug 要補回歸斷言並說明既有測試為什麼沒抓到；測試要走使用者的真實路徑；動到 `js/merge.js` 或 `workers/` 時 Worker 先部署、客戶端後推。
- **R9 新寫的測試若依賴日期**：fixture 不要寫死「相對今天」的筆數或偏移；要嘛固定時鐘，要嘛斷言引用程式自己算出來的數量。（既有測試不在這次範圍內回頭檢查，留給下一次全面檢測。）

## 7. 測試要求（`scripts/affectedtest.mjs`，純 Node）

紀律照舊：每條斷言都要證明會紅（手動突變，回報裡逐條寫「改壞了什麼 → 哪條紅 → 改回去綠」）；母體非空；檢查器有對照組；含 regex 的程式碼用 Write／Edit 工具寫檔，不經 heredoc。**改動檔案清單用 `git show --stat --name-only <commit>` 實際查出來的為準，不要照抄 §1 表裡的摘要**（那是勘查員的整理）；查出來的清單寫死在測試裡當 fixture（歷史不會變）。

| T14 | 輸出含「這不是全綠」與正確的 N/M；命中 C 時含「放大到全套」 | M 從鏈數出來，不寫死 | 把 N/M 寫死 → 在假鏈長度不同的對照組上紅 |
| T15 | 文件對程式（兩段式）：先斷言 STATUS「測試」節有「完整的鏈 N 支」這句，再斷言 N＝鏈的實際長度 | 兩段式：文件那句被刪掉時要紅，不是靜默通過 | 把 STATUS 的數字改錯 → 紅；把那句刪掉 → 紅 |

**這一版自己要跑什麼**：`npm run test:affected`（依新規則，這次只改了 `scripts/` 新檔、`package.json`、文件 → 底線＋`affectedtest`）。**不用跑完整 `npm test`。** 另外請實際示範一次：隨便挑一個真實的小改動情境（例如假裝改了 `js/views/album.js`，用 `npm run affected -- --files js/views/album.js` 之類的方式餵進去，不要真的改檔），把挑選器的輸出貼進回報，讓 Yolin 看得到平常一版大概會跑哪幾支。

## 8. 文件、版本、回報格式

- 一個 commit（或照你的習慣分成「工具＋測試」與「文件」兩個）；不 bump、不部署；push 用 `git push origin main`。本 repo 是 **public**：commit 之後、push 之前，對新增行做一次公開前自查（金鑰或 token、email、本機使用者名稱、本機路徑四類，每一類先確認對照組命中），結果寫進回報。
- 回報請逐條對照：R1–R9 各怎麼落地；T1–T15 每條的突變與結果；七個案例各挑中幾支（這就是省了多少的實據）；§6 的五處文件修改各改了什麼；示範情境的輸出；實測與推論分開寫；工單沒預期到的狀況。
- 你如果認為某個放大器太寬（平常每版都命中全套，等於沒放寬）或太窄（某個案例要靠運氣才挑得到），**不要自己改規則，先回報**：附上數據（七個案例各挑中幾支、最近十個版本的 commit 如果用這套規則各會跑幾支），由統籌者調整。「最近十個版本各會跑幾支」這個統計請直接做，它是判斷這套規則實不實用的依據。

## 9. 統籌者做的取捨（Yolin 可以否決）

| # | 取捨 | 理由 | 代價 |
|---|---|---|---|
| 1 | 做自動挑選器，不用人工對照表 | 兩個 App 的人工判斷都漏過（§1）；StockDiary 後來也是改成工具才穩 | 多三個腳本檔、多一支測試 |
| 2 | 骨架類改動（`sw.js`、路由、`index.html`、合併語意、Worker）仍然跑全套 | 案例 ① 無法預測；合併錯誤會永久寫進 D1。這類不算「小改動」 | 這類改動的版本省不到時間 |
| 3 | 「發版那一次跑全套」**不採納**（勘查員的建議） | 本 App 每次 push 就是上線；Yolin 9/12 的原話是「不用每次上線都做全面測試」 | 上線的版本不保證全套跑過——這正是 Yolin 接受的取捨，由定期全面檢測與每版 `sweep` 兜底 |
| 4 | 每版回報附「距上次全面檢測 N 版／D 天」，但不自動跑 | 日期走過去造成的失敗只有全測抓得到；提醒一行的成本是零 | 回報多一行 |
| 5 | 不為了量耗時專程跑一次全套 | 與這次裁示的方向相反；下一次全面檢測時順便量 | 在那之前不知道全套要多久 |

## 11. 修訂一（2026-09-19，統籌者對執行時回報的三個規則問題的裁決）

> 狀態：**已執行（2026-09-19）**；1-A、1-C 全數落地，1-B 的「閉包停在 app.js」落地，但 D 仍不響（`js/views/` 目錄引用是另一個入口），「只被 app.js 閉包涵蓋的真實檔」那條斷言前置不成立、未加，數據見 `docs/STATUS.md`「測試範圍」，待統籌者裁決。原說明：三個問題都成立；你沒有自己改規則、附了數據回報，這正是 §8 要的做法。第 1 個是規格的疏失：統籌者明知本 App 每版都 bump `sw.js`，卻把整個 `sw.js` 放進放大器 C。

**修訂 1-A：`sw.js` 只改 VERSION 那一行，不算放大器 C。**
- 挑選器維持純函式（不讀 git）。由呼叫端 `run-affected` 判斷：`sw.js` 的 diff 若**只有** `VERSION` 常數那一行有變動，就把它當成「版本行改動」傳進去（具體怎麼標記由你定，例如改傳一個虛擬路徑）；挑選器對它的處理＝不觸發 C，只加跑 `updatetest` 與 `nearbytest`（案例 ⑦ 當年的兩個受害者，當作便宜的保險）。`sw.js` 有任何其他行改動（SHELL 清單、快取策略…）→ 照舊命中 C、全套。
- 判斷不出來（diff 取不到、`sw.js` 是新檔、VERSION 那一行的樣式對不上）→ 保守：當成命中 C。
- 測試：(a) 案例 ⑦ 仍然必須放大到全套（它改的是快取策略）；(b) 新增一條：只改 VERSION 行 → 不是全套、結果含 `updatetest` 與 `nearbytest`；(c) 對照組：VERSION 行＋另一行一起改 → 全套。突變：把「只改 VERSION 行」的判斷改成永遠成立 → (a) 或 (c) 紅；改成永遠不成立 → (b) 紅。

**修訂 1-B：閉包不穿過 `js/app.js`；放大器 D 因此恢復作用。**
- `js/app.js` 是整個 App 的入口，它的閉包就是全部程式檔，拿它來算「誰涵蓋誰」沒有鑑別力。改成：引用 `js/app.js` 的測試只算**直接引用** `js/app.js` 這一個檔，閉包展開遇到 `js/app.js` 就停。R3 規則 3 與放大器 D 的「有沒有人涵蓋」都用這個新定義。
- 這會讓 D 開始響。**要防它響得太頻繁**（那又等於沒放寬），所以 D 的放大目標由數據決定，規則我先訂好、你照數據套用，不算你自己改規則：重做「最近十個版本」的統計；**D 觸發 ≤ 3 版 → D 維持放大到全套；D 觸發 ≥ 4 版 → D 改成放大到「放大器 A 的那一組 ∪ 放大器 B 的那一組」，並照樣在輸出裡點名是哪個檔沒人認領**。採用了哪一個、十版裡 D 各是被哪些檔觸發的，寫進回報與 STATUS。
- 測試：T12 照舊（`js/__nobody.js` → 觸發 D、點名）；新增一條用真實的圖：找一個「只被 `js/app.js` 的閉包涵蓋、沒有任何測試點名」的真實程式檔，斷言改它會觸發 D（前置：先斷言這樣的檔至少存在一個，並在回報列出共有幾個——這個數字就是目前測試點名不到的程式檔數量，Yolin 會想知道）。突變：讓閉包重新穿過 `js/app.js` → 這條紅。

**修訂 1-C：`imgtest` 加進放大器 A，拿掉 `KNOWN_GAPS`。**
- 案例 ② 就是畫面結構改動讓它紅的；規格要求「當年受波及的每一支都挑得到」，已知缺口不該留著。A 從 8 支變 9 支。
- 測試：案例 ② 的嚴格回放必須挑得到 `imgtest`；`KNOWN_GAPS` 這個機制整個移除（留著它，下一個缺口就會被靜默收進去）。突變：把 `imgtest` 從 A 拿掉 → 案例 ② 紅。

**追認**：你加的那條保守退路（改到不屬於任何已知類別、也沒有測試引用的檔，例如 `icons/`、`media/`、`manifest.webmanifest` → 全套）保留。這類改動很少，寧可多跑。

**做完之後**：重跑 `affectedtest`；重做「最近十個版本各會跑幾支」與「七個案例各挑中幾支」兩張統計，新舊並列寫進回報；STATUS「測試範圍」小節的放大器表、「已知的規則問題」那一段跟著改（問題解掉的就刪掉那一條，不要留著過期的描述）。其餘照 §8（不 bump、不部署、push 前公開前自查、回報不准寫全綠）。**驗收標準補一條**：十版統計裡，至少一半的版本明顯少於全套；達不到就再回報，不要硬湊。

## 10. 驗收

Yolin 不需要實機操作。看三樣：回報裡七個歷史案例全部挑得到；「最近十個版本各會跑幾支」的統計顯示多數小改動遠少於 44 支；之後每一版的回報都寫「N/M 支」與「距上次全面檢測」那一行，沒有人再把部分測試寫成全綠。
