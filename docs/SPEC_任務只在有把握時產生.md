# SPEC_任務只在有把握時產生 — 對不上內建景點資料庫的地點，不猜、不出題，留給使用者自己加

> 狀態：已執行（2026-09-21、v1.74.0）
> 規劃：Fable 5.1 統籌 Session，2026-09-21。決策來自 Yolin 2026-09-21 的兩段原話（§8）。事實依據：三位 Opus 勘查員 2026-09-21 的唯讀實查（含用真的 `generate.js` 跑 28 個地名、對 Nominatim 實測 35 個地名；行號以你現在讀到的為準）。

## 一句話

把設計目標從「永不落空」改成「**沒把握就留白**」：只有對得上策展資料庫（`data/places/`）的地點才自動產生任務與介紹文字；其餘地點不出任何情境題，畫面上給「＋新增任務」與「＋照片」兩個一步就到的入口。

## 1. 現況（勘查事實）

- 唯一產生器 `js/quests/generate.js` 的 `generateForTrip()`；三個入口：`create.js`（建立旅程／貼行程文字／匯入）、`findspot.js` 的 `addSpot()`（搜尋景點加入、手動輸入）、`trip.js` 的 `regenerate()`（「補齊任務」）。另有 `spot.js` 的 `offerTimeFixQuests()`（改時間後換掉時段不合的任務）。
- 策展資料庫 135 筆；命中靠 `matchPlace()`（正規化、去分店後綴、子序列 `looseHit`，門檻 60 分）。
- **沒命中就用名稱猜**：`inferType()` 拿 `data/templates.json` 的 `typeRules` 做單字 `includes`（「山」→ mountain、「海」「湖」→ water、「大佛」→ 古蹟…）→ `theme.js` 的 `themeForSpot()`（`byName` 12 條 regex → `byTag` → `byType` → 預設 `journey`）→ `data/phrases.json` 出 3 個任務與一段介紹。`generate.js` 檔頭註解寫明目標是「永不落空」，`composeQuests` 末端還有 generic 保底。
- **Yolin 的真實案例**：宜蘭「白雲山鹿」是早餐店，名稱含「山」→ 自然景點 → 任務「拍下 白雲山鹿 最開闊的一景」「一條路的盡頭」「光影最好的一刻」；他們真的去完成了，「光影最好的一刻」配到的是一碗食物。勘查員實跑：好樂迪KTV 中山店→「光影最好的一刻」、海底撈→「在海底撈面海合照」、大佛牛排→「參拜或參觀的一刻」、家樂福內湖店→「海邊撿到的東西」。15 個餐飲／住宿／超市／KTV 裡 6 個明顯錯、7 個空洞、2 個對。
- **「優化判斷」評估過，救不了**（Yolin 要求先評估這條路）：(1) 名稱推測先天分不出「白雲山鹿」是店還是山，調規則只會從 40% 錯降到比較少，不會到零。(2) 地圖服務（Nominatim）的類別本身可信——實測 35 個地名裡**沒有任何一個餐飲、住宿、商店被標成自然或風景類**——但只有 57% 查得到而且夠具體，17% 是查錯地物（白雲山鹿查到的 5 筆全是天津的路），而且**只有「搜尋景點加入」這條路拿得到類別**；貼行程文字、手動輸入這兩條路（白雲山鹿最可能的來源）現在與未來都拿不到。所以這一版不用地圖類別出題；見 §2 非目標與 §7。
- **少產生會弄壞的兩件事**：(a) 照片一定要帶 `questId`（`addphoto.js`），上傳鈕只畫在任務列上——沒有任務的地點**沒有地方放照片**；(b) `trip.js` 的 `nextIncompleteSpot()`／`focusSpot()` 把 `total === 0` 當成未完成——「現在這一站／帶我去下一站」**會永遠卡在沒任務的地點**。完成率（`store.js` 的 `tripProgress`／`spotProgress`）以任務數為分母，0 任務的地點本來就不算，徽章與海報不依賴「每個地點都有任務」。
- 使用者自己新增任務的入口有，但要 5 步（行程頁 →「調整每天的行程」→ 展開景點 →「✏️ 任務」→「＋ 新增任務」→ 兩個對話框）。手動建的任務 `source: 'custom'`。
- 任務的 `source`：`curated`／`must`（策展）、`template`／`generic`（猜的或保底）、`custom`（使用者）。「有沒有被改過」可由 `quest._f.text > quest.createdAt` 判斷。
- 同步：`merge.js` 逐筆 id 合併、沒有去重——兩台裝置離線各自產生同標題的任務會重複。
- 順帶查到的兩個現行 bug（`js/geocode.js`）：`format=jsonv2` 回傳的欄位是 `category` 不是 `class`，所以 `hit.class` 永遠是 `undefined`——類別中文後援從沒作用、`rankHits` 給景點類的 +1 分從沒加過（晶華酒店因此排出 `landuse/commercial` 而不是旅館）；`rankHits` 只認 `type === 'station'`、不認 `train_station`，「宜蘭火車站」排序後第一名變成黑龍江的車站。
- `phrases.json` 的 `food.blurb` 有一句寫死「{name}是台南人從小吃到大的味道。」

## 2. 目標與非目標

**目標**：G1 對不上策展資料庫的地點，**不出現任何猜出來的情境文字**——任務、提示、介紹、依猜測挑的表情符號都算。G2 沒有任務的地點照樣能放照片、能自己加任務，而且一步就到。G3「下一站」不會卡住。G4 策展命中的地點，行為一個字都不變。G5 已經存在的旅程不被自動改動。

**非目標**：不用地圖服務的類別出題（這一版）；不新增 spot 的同步欄位（不動 `merge.js` 的 `TRACKED`）；不回溯替舊旅程的地點補類別或改題；不改策展資料庫的內容；不讓使用者替地點選類別（Yolin 沒要，多一個要選的東西）；不改完成率與徽章的算法。

## 3. 規則

- **R1 出題的唯一依據是策展命中。** `generateForTrip()`：`matchPlace()` 命中 → 照現行產生（`curated`／`must`／該景點的主題題）；沒命中 → **不產生任何任務**。`inferType()`、`themes.json` 的 `byName`／`byType`、`composeQuests` 的 generic 保底，對沒命中的地點一律不得用來產生任務、提示或介紹文字。檔頭「永不落空」的註解改成現在的設計目標與理由（引 §8 原話）。
- **R2 猜出來的類型不得產生任何使用者看得到的描述。** 沒命中的地點：`blurb` 留空、主題用中性的 `journey`（或等同的中性值）決定外觀、表情符號用中性的地點圖示。請列出 `inferredType`／猜出來的 `theme` 的**全部讀取端**寫進回報；只允許留著「使用者看不到或無害」的用途（例如預設停留分鐘數）。
- **R3 策展比對收緊。** `matchPlace()` 的子序列寬鬆比對會讓「○○山莊餐廳」對到某座山。請用現有的策展 135 筆 × 一份反例清單（§6 T2）量現在的誤命中，把門檻或規則收到**反例 0 命中、正例不掉**；做不到兩全就以反例 0 命中為先，掉了哪些正例列進回報。
- **R4 沒有任務的地點的畫面。** 行程頁該地點的卡片上，原本放任務列的位置顯示兩顆按鈕：**「＋新增任務」**（直接開既有的新增對話框，1 步）與 **「＋照片」**。文字誠實：不要寫「系統不確定這是什麼地方」之類的解釋，按鈕本身就夠。有任務的地點在任務列最後也放同一顆「＋新增任務」（把 5 步縮成 1 步，兩種地點一致）。
- **R5「＋照片」的資料做法。** 照片仍然掛在任務底下（不動照片與同步的資料結構）：第一次按「＋照片」時，替這個地點建立**一筆中性的照片任務**再開上傳——標題「{地點名稱} 的照片」、沒有提示、`source: 'photo'`（新值）、`kind` 沿用你認為合適的既有值。**id 用確定性的 `q-photo-<spotId>`**（或等同的確定性做法）：兩台裝置離線各按一次也只會是同一筆，合併後不重複。這一筆存在之後，該地點就照一般有任務的地點顯示。
- **R6「下一站」不卡住。** `nextIncompleteSpot()`／`focusSpot()`：0 任務的地點不算未完成，直接跳過；全部地點都沒有任務時的行為你定（不能丟錯、不能空白一片），寫進回報。
- **R7「補齊任務」與改時間。** `regenerate()` 只替策展命中的地點補；`offerTimeFixQuests()` 對沒命中的地點不做事。「補齊任務」沒有東西可補時的提示文字照實寫。
- **R8 已經存在的旅程：一律不動。** 舊旅程裡已經產生的任務（含猜出來的）原封保留，不自動清、也**不做「移除自動猜的任務」的按鈕**（Yolin 2026-09-21 決定，理由見 §8 第 6 項——是「現在沒有需要清理的存量」，不是永久否決）。
- **R9 順手修的 bug（分開 commit）**：`geocode.js` 讀 `category`（保留對 `class` 的相容）；`rankHits` 把 `train_station`、`subway_station` 與 `station` 一樣看待。`phrases.json` 那句寫死「台南人」的介紹改成不帶地名的說法或刪掉。
- **R11 任務句的時段守門與幾句明顯不合的句子（分開 commit）。** 留白之後，任務句只會出現在策展景點上——主題是確定的，但句子仍可能對不起來：(a) `compose.js` 的 `timeWindow()` 在 `startMin` 是 null 時回 null、`phraseOk` 就**全部放行**，而「幾點到」預設是未設定，所以標了 `when: morning／evening／night` 的句子（「晨光裡的 {name}」）在最常見的情況下照出不誤。改成：**沒填時間時，帶 `when` 的句子一律不出**（不知道幾點去，就不出有時段假設的題）。(b) `nightmarket` 整組沒有任何一句標 `when`，卻滿是「一到晚上就熱鬧起來」「燈火下合照」——補上 `when`。(c) `heritage` 的提示「拍下有人在淨手、上香、或靜靜看展的畫面」把三種場所寫在同一句——拆開或改成不假設場所的說法。(d) 其餘你掃過認為「主題對了仍可能對不起來」的句子列進回報，**只改你有把握的，其餘列清單給統籌者**，不要大改寫。策展庫 135 筆用改完的句庫重新產生一次，前後差異（哪些景點少了哪幾句）列進回報；任何策展景點因此變成 0 個任務 → 回報，不要自己補句子湊數。
- **R10 文件**：STATUS 記下這次的設計原則——「**寧可不產生，也不要產生錯的**；猜的東西不准變成使用者看得到的字」，以及地圖類別那條路的評估結論（§1、§7），免得日後有人又把猜測接回來。

## 4. 與現有規則的交互

| 現有的東西 | 會不會衝突 | 結論 |
|---|---|---|
| 完成率、徽章、海報 | 0 任務的地點不進分母；`foodie` 徽章要 `foodTotal >= 2` | 不改算法。策展的食物景點不受影響；回報裡說明 `foodie` 會不會因此更難拿 |
| 旅伴同步 | 新的 `source: 'photo'` 值、確定性 id | 不新增欄位；舊版 App 收到 `source: 'photo'` 的任務要能照常顯示（請實查；版本混搭是你 STATUS 記過的坑）|
| AI 匯入（OCR／貼文字）| 匯入後一口氣建一堆地點，多數對不上策展 | 想要的結果：行程照樣建起來，只是大部分地點沒有任務。匯入完成的提示若寫了「已產生 N 個任務」之類的數字，照實 |
| `importtest`「每個景點都出了任務」| 直接相反 | 改寫成新語意（§6 T6），不是刪 |
| 測試範圍挑選器 | 動到 `js/quests/**`、`js/views/**`、`data/*.json` | 照你現行的放大器規則；這一版改到產生器核心，統籌者建議直接跑全套並**順便量全套耗時**（STATUS 的「整套上限：待量」就可以填了）|

## 7. 之後可能的下一步（這一版不做，記下來）

用地圖類別替「搜尋景點加入」的地點出題：類別本身可信，但要同時過兩關才採信（結果名稱與輸入實質相符、座標離行程中心在合理範圍），用白名單對到主題，籠統的類別（`building=yes`、`landuse=*`、`place=*`、`tourism=attraction`）一律留白；還要新增 spot 的同步欄位（動到同步的記錄格式，要先問 Yolin）；而且 `phrases.json` 有一批句子即使主題判對也可能對不起來（夜市主題全組沒標時段、自然主題假設大面積步道、古蹟提示把淨手／上香／看展寫在同一句；`compose.js` 的時段守門在沒填時間時整個失效）。**先上這一版、看 Yolin 用起來的感受，再決定要不要做。**

**2026-09-21 補記**：Yolin 另外提議「讓使用者手動貼 google 路徑後由系統讀完評論後產生任務」。統籌者評估：讀評論不採（一次最多 5 則、最貴的計費級、把 Places 內容交給 LLM 做衍生內容並同步儲存有條款風險）；但 Google Places 的 `primaryType` 是比 OSM 更完整、可信的類別來源（白雲山鹿在 Google 上是早餐店），而且不必貼連結——把「搜尋景點加入」改打 Places Text Search、匯入後自動補查，使用者零動作，用量在免費額度內。**前提是建行程的人要有 Google 金鑰，而你的 STATUS 記著至今沒有人辦過。**所以這仍然是下一步：沒有金鑰的行程永遠走這一版的留白；有金鑰的行程之後才可能多一條「類別明確才出題」的路。Yolin 2026-09-21 已說會去辦金鑰；金鑰到位並實測可用之後，統籌者才會交付那一份規格（還要他同意新增同步欄位、三代理投票、覆核 Google 現行價目與條款）。這一版不要為它預留任何程式。
