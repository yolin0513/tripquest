## 一句話

分帳現在有六個地方會讓錢對不起來：**使用者選不了付款人與分類**（每一筆都記成第一個人付的餐飲）、查不到匯率時把日圓當台幣加總、份數全填 0 的那一筆沒有任何人分攤、參與者或付款人是空的時候收支不守恆、除不盡時畫面上的「應收」跟「結清方案」差一分錢。v1.74.2 已經把安全網（`moneytest` 91 項、`settletest` 26 項）鋪好，這一份把缺陷修掉，並在安全網上當初留註解的位置補斷言。

## 1. 現況（統籌者讀 `6507bac` 得到的）

- **chip 選不動**：`js/views/expenses.js` 的 `field(label, control)` 回傳 `h('label', { class: 'form-field' }, …)`，把「分類」「誰付的」整排 `<button>` 包在一個 `<label>` 裡。點第二顆之後 `drawCat()`／`drawPay()` 用 `replaceChildren` 重繪，被點的那顆離開了 DOM，點擊冒泡到 `<label>` 時被轉發給排在第一個的控制項——選擇落回第一顆。你實測：點「小美」得到「阿公」。
- **同一個 `field()` 另外還有兩份**：`js/views/create.js`（約 360 行）、`js/views/spot.js`（約 327 行），寫法一字不差。它們包的是不是「會重繪的一排按鈕」，統籌者沒查。
- 「分給誰」那一格也經過 `field()`：外層 `<label>` 裡面是每個成員一個 `<label class="exp-part">`（內含 checkbox，自訂比例時還有一個數字輸入框）加一顆切換按鈕——**巢狀的 label**。勾選後 `drawParts()` 同樣會重繪。這一格有沒有同類的轉發問題，你的回報沒提，統籌者也沒實測。
- CSS 沒有綁標籤名：`.form .form-field`、`.exp-form .form-field`、`.page.compact .form-field`、`.form-label` 都只認 class（統籌者 grep 過 `css/`）。
- `settleCore({ expenses, baseCurrency, ratesObj })` 是純函式；`toBase()` 查不到匯率時 `return amt`（D1）；`sharePerMember` 的 `total … || 1`（D2）；`participants` 空回 `{}`（D3）；`if (e.payerId)` 只保護入帳那一半（D4）；`minTransfers` 的 `eps = 0.01`、畫面上「打平」的門檻是 `0.5`，金額到顯示那一刻才四捨五入（D5）。

- `fmtMoney` 的小數位：`currencyInfo(code).zero` 為真 → 0 位，否則 2 位。

## 2. 目標與非目標

**目標**：G1 使用者用手指點得到他要的付款人與分類；G2 查不到匯率的錢不混進合計，畫面講得出有多少錢沒算進去；G3 任何一組存得進去的花費，結清核心都守恆（每人淨額總和為 0）；G4 畫面上同一筆錢的每一個數字互相對得起來（應收的總和＝結清方案的總和，一分不差）。

**非目標**：不動花費的資料結構、不新增同步欄位、不動 `workers/**`；不改匯率來源與快取；不加新相依；不做「手動輸入匯率」；不改 `minTransfers` 的貪婪策略（只改它吃進去的數字與門檻）；**不新增卡片、對話框、設定項**——提示一律用既有的那幾個位置（`form-hint`、`toast`、明細的副標）。

## 3. 規則

### 第一段：R0（獨立 commit、獨立一版、最先上線）

- **R0 一排按鈕不放在 `<label>` 裡。** `field()` 分成兩種用法：包**單一輸入框**的維持 `<label>`（點標籤文字會聚焦輸入框，這是對的）；包**一組控制項**（chip 排、參與者清單＋切換鈕）的改用 `<div class="form-field" role="group">`＋`<span class="form-label">`，並讓群組唸得出名稱（`aria-labelledby` 或 `aria-label`）。class 不變，所以版面不該有任何變化——請用 `layouttest` 或你判斷合適的既有測試確認。
- **R0 的範圍要查三個檔**：`expenses.js`、`create.js`、`spot.js` 的每一個 `field(…)` 呼叫點，列出它包的是什麼；包的是一組控制項的，全部照上面改。另外全 `js/views/` 找一次「`<label>` 裡面放了會重繪的按鈕」的同型寫法，有就一起修、沒有就在回報寫「查過、沒有」。
- **「分給誰」那一格請實測後回報**：用真的滑鼠點第二、第三個成員的名字與勾選框，第一個成員的勾有沒有跟著變；自訂比例時點份數輸入框、打字，有沒有跳走；點「改成自訂比例」按鈕有沒有副作用。有問題就在 R0 一起修；沒問題也照改成 `<div>`（巢狀 label 本來就不合規），並寫明實測結果。

### 第二段：R1（D1，Yolin 已核准）

- **R1 查不到匯率的花費，整筆不進合計與結清。** `settleCore` 對「幣別不是基準幣別、而且 `convert` 回 `null`」的花費：不加進 `grand`、不加進 `byMember`、不動 `balances`（付款與分攤兩邊都不算，所以守恆不受影響）。另外回傳 `unconverted`：依幣別分組的 `{ code, total（原幣別加總）, count }` 陣列，順序穩定。`missingRate` 照舊（`unconverted` 非空時為 `true`），`count` 仍是全部筆數；另給一個「有算進去的筆數」。**`toBase()` 不准再有「查不到就回原值」這條路。**
- **R1 畫面**（只用既有的 `form-hint` 那個位置，取代現在那句「換算可能不準」）：每個查不到的幣別一行，意思是「另有 ¥12,000（2 筆）查不到匯率，沒有算進合計與結清方案」（措辭你定；金額用 `fmtMoney` 以原幣別顯示；要講出「沒有算進去」，不准用「可能不準」這種講不清楚的話）。「共 N 筆」要分得出幾筆有算、幾筆沒算。結清方案那一區在有未換算花費時，同一句的意思要再出現一次（標題下方一行即可）——使用者最可能只看那一區就去轉帳。
- **R1 全部都查不到時**（例如第一次開、離線、`rates` 是 `null`，而這趟又沒有任何基準幣別的花費）：合計不准顯示成 0 元（共用慣例 §4：不用 0 冒充算不出來）。照實寫「還沒有可以換算的花費」之類，結清方案那一區寫「查到匯率之後才算得出來」，不要顯示「大家打平 🎉」。
- 明細每一筆本來就用原幣別顯示，不用改。

### 第三段：R2–R4（D2、D3、D4）

- **R2 份數全是 0（D2）。**
  - 表單：選了自訂比例、而有參與的人份數加起來 ≤ 0 → 儲存時擋下，用既有的 `toast`（比照「至少選一個人分」），意思是「份數至少要有一個人大於 0」。負數一律當 0（輸入時就夾住）。
  - 核心：已經存在的資料（同步來的、這一版之前記的）仍可能全 0 → `sharePerMember` 在有效份數總和 ≤ 0 時**退回參與者平均分**，`total … || 1` 那條路拿掉。**這是替使用者補了一個他沒填的東西，所以畫面要講**：那一筆在明細的副標（現在寫「阿公 付 · 3 人分」的那一行）多一句，意思是「份數都是 0，先照平均分」。只有這種筆才出現。
- **R3 參與者是空的（D3）。** 表單已擋。核心：當成「只有付款人自己分」（淨額不變、守恆）；`grand` 照算。明細副標現在會寫「0 人分」，照實，不用改。
- **R4 付款人是空的、或付款人不在這個群組的成員裡（D4）。** 表單造不出來。核心：整筆不進 `balances`（不扣任何人、也沒有人入帳），`grand` 照算，回傳裡計數（例如 `noPayer`）；畫面在同一個 `form-hint` 位置多一行，意思是「有 N 筆沒有付款人，沒有算進結清方案」。
- **只查只回報（不在這一份修）**：旅伴有沒有任何一條路會被移除或換掉 id（旅程設定、同步合併、匯入）？如果有，他付過的與參與過的花費現在會怎樣——`balances` 會出現不在 `members` 裡的 id，「每個人」那一區不列他、但結清方案會出現「（未指定）給阿公」。請用**自己造的資料**實測，回報事實；要不要修另外決定。

### 第四段：R5（D5）

- **R5 結清以基準幣別的最小單位做整數運算。** 在 `settleCore` 算完每人淨額之後、丟給 `minTransfers` 之前：把每人淨額換成最小單位的整數（兩位小數的幣別 ×100、零小數的幣別 ×1，小數位由呼叫端傳進來，預設 2；`settleTrip` 這層外殼用 `currencyInfo(base).zero` 決定），四捨五入；捨入後總和若不是 0，把差的那幾個單位**用確定性的規則**分給人（建議：絕對值最大的先、同值比 id 字串），讓總和回到 0。`minTransfers` 在整數上跑，門檻改成「不等於 0」，輸出再除回去。結果：**畫面上每個人的應收／應付、與結清方案每一筆，都是同一組整數換出來的，加起來一定相等。** 三人分 100 會變成 66.67 ＝ 33.34 ＋ 33.33（誰多一分由上面的規則決定，同一組資料每次都一樣）。
- **R5 畫面**：「打平」的判斷改成淨額（捨入後）等於 0；現在的 `0.5` 門檻拿掉（它會讓「應付 0.40」顯示成打平、但結清方案裡又有一筆 0.40）。`balances` 回傳的就是捨入後的值；若你認為要同時保留未捨入的值給別處用，另開欄位、不要讓畫面兩種都拿得到。
- `sharePerMember` 回傳的原幣別精確值不動。「每人平均」照舊（那是資訊，不參與結清）。
