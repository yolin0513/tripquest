### `TRACKED` 的分歧（2:1 進）
- **代理 2、3（進）**：一筆裡不同欄位同時被兩人改（一人勾、一人改字；一人改住宿名、一人改日期）兩邊都留下。**而且只能在第一版決定**：先不追蹤、以後再升級，這一版的手機就會變成「改得到卻不更新 `_f` 的舊版」，帶著舊 `_f` 上傳、每組都輸（`merge.js` 94–97 行的警告、`expense` 不能進 TRACKED 的同一個理由）。全新型別沒有舊記錄，每筆都由新版 `put` 寫、`_f` 一開始就齊。
- **代理 1（不進）**：不動 `merge.js`、不動 Worker、完全沒有部署順序；同一筆不同欄位同時被改很少見、被吃掉看得到可以重做。也同意「要不要追蹤一旦上線就不能改」。
- **怎麼採**：多數決取「進」。保守面的代價是**要動 `merge.js`、Worker 先部署**——v1.75.0 本來就改了 `merge.js`、本來就要 Worker 先部署，沒有多出一種新風險；反過來，「不進」是**之後再也改不回來**的那一邊。三票一致點名：既有型別的欄位組不動，所以不會出現上一次「既有記錄被補 `_f` 鍵、觸發修復寫回 D1」的疑點（推論，部署前用 `workertest` 驗）。
- **現役 Worker 會刪掉未知型別的 `_f`**（`merge.js` 214 行，代理 2、3 都查到）：客戶端先上的話，新型別在 D1 上退化成整筆後寫者贏。所以順序是硬性的。

### 欄位（取三票的交集；只有一票提的照多數）
- **`flight`**：`tripId`、`flightNo`（照打的存，只去頭尾空白）、`depDate`、`depTime`（機票上的起飛當地時間）、`depPlace`、`arrDate`（**使用者填，不從起飛日推**）、`arrTime`、`arrPlace`、`note`。欄位組：`no:[flightNo]`、`dep:[depDate, depTime, depPlace]`、`arr:[arrDate, arrTime, arrPlace]`、`note:[note]`。日期與時間同組（不合出「A 的日期配 B 的時間」）。地點、備註代理 3 沒列，代理 1、2 有 → 收。
- **`buy`**（代理 2、3 的名字；代理 1 叫 `buyItem`）：`tripId`、`text`（不可空）、`done`（布林，預設 false＝還沒勾的真實狀態）、`doneBy`（只記實際選過「我是誰」的人，沒有就 null、畫面不寫名字）。欄位組：`text:[text]`、`done:[done, doneBy]`。這一版沒有 `order`；以後要排序就加新組 `order`（加新組是安全的）。
- **`stay`**：`tripId`、`name`（不可空）、`checkIn`、`checkOut`（可 null）、`address`、`note`。欄位組：`name:[name]`、`dates:[checkIn, checkOut]`、`addr:[address]`、`note:[note]`。不存晚數、不存第幾晚、不存 `spotId`。`address` 代理 3 併在 note，代理 1、2 分開 → 分開。
- `groupId`：代理 1 主張跟 `expense` 一樣也帶（`store.js` 依它判群組）；另兩票沒提。**明早實作時讀 `store.js` 判群組的那段決定**（只影響歸屬，不影響合併）。

### 推測值的界線（三票一致）
- 不從班號推航空公司或時刻；不從機場推時區；不拿手機時區當起飛地時區（回程航班手機多半還在本國時區）；不算飛行時長；不拿航班日期改 `trip.startDate`。
- 不從站名（「飯店」「民宿」）、花費類別「住宿」、`geocode.js` 的 `hotel: '住宿'` 或 `maps.js` 的 GENERIC 推「這是住宿」——代理 1 點名這兩處最容易被接過來，明文禁止。
- 晚數＝使用者填的退房日減入住日，屬於算術、可以顯示；缺任一個日期就寫「還沒填日期」，不寫 0 晚。「第 N 晚」只在日期落在行程內才寫。

### 舊資料（三票一致）
現有行程三種都是 0 筆：各自一行空狀態（「還沒加航班」）＋新增鈕；不顯示「0 項」「0 晚」、不放範例、不用行程日期預填。首頁與行程頁既有的「還有 N 天出發」不動。

### 已知、接受的行為（三票都寫）
- A 刪了某項、B 在那之後（時間戳較晚）改它 → 那一項回來（跟 spot 現在一樣）。多一項、不是少一項；要寫一條斷言把它釘住。
- 舊版行程頁在別人改這三種記錄時多重畫一次（`views/trip.js` 的 `tripSignature` 看所有同 `tripId` 記錄），無害（推論）。

## 部署順序
1. `js/merge.js` 的 `TRACKED` 加 `flight`、`buy`、`stay`；既有型別的欄位組不動。區網自架的 `server/index.mjs` 也 import 同一份，要一起更新（代理 2、3）。
2. **Worker 先部署、客戶端後推**。D1 結構不改（整筆存 `json`）。
3. 沒有資料遷移；**沒有任何一步會刪除或改寫使用者既有的資料**（三票一致，推論）。
4. 部署前 `workertest` 補兩種情境（代理 1、3）：未知型別整筆存整筆回；舊的那份推上去會輸；以及「既有記錄在新舊 Worker 上寫入次數都是 0」。各配突變。

### Yolin 的答覆（2026-11-05 確認，經 Dispatch 轉達）
原話：「這四題都 OK」。四題全部通過：
1. 航班倒數只到「天」——✅
2. 分享代碼不帶航班／住宿／待買（完整備份會帶）——✅
3. 待買清單不能手動排序——✅
4. 刪除與較晚的修改同時發生時，刪掉的項目會回來——✅ **接受，這是設計，不是 bug。**
   - **實際後果（給以後接到回報的人）**：家人 A 在自己手機上刪掉一項待買（或一筆住宿、航班），如果家人 B 的手機在 A 刪除**之後**又改了同一項（例如 B 離線時勾了它、晚點才連上），同步後那一項會**重新出現**——A 會覺得「我明明刪掉了」。原因：刪除是墓碑（`deleted: true`），墓碑跟修改比的是整筆的時間戳（`merge.js` 墓碑走整筆語意），較晚的修改贏。景點（spot）現在就是同樣的行為。
   - 取捨：錯的方向是「多出一項」而不是「默默少掉別人剛改的東西」。實作時寫一條斷言把這個行為釘住，回報被當成 bug 時指向這一節。
