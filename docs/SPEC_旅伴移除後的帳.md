## 一句話

從旅程設定移除一位記過帳的旅伴，現在不會有任何提醒；移除之後，他付的錢不進結清，他在別人那筆裡的分攤卻還在帳上，結清方案寫成「（未指定） 給 阿公 NT$100.00」，「每個人」那一區又不列他。這一份做兩件事：**移除前講清楚（R1）**，**移除後帳面照樣叫得出他、錢照樣守恆（R2）**。不改資料結構、不動同步、不新增畫面元件。

## 1. 現況（統籌者讀 `666646c` 得到的）

- **移除旅伴＝軟刪除**：`js/views/trip.js` 的 `memberEditor()` 裡那顆 🗑️ 呼叫 `store.remove(m.id)`，而 `remove()` 是 `patch(id, { deleted: true })`——整筆欄位（含 `displayName`）都留著，只多一個 `deleted`。`membersOf()` 會把它濾掉；`getRaw(id)` 拿得到。
- **墓碑同步時名字還在**：`merge.js` 遇到 `deleted` 走整筆語意（`mergeRecord` 約 157 行）；Worker 與本機 server 另外組的「精簡墓碑」只用在 `memberPos`（位置），不碰 `member`。所以別台手機上，已移除旅伴的名字一樣查得到。
- **移除前的確認只管照片**：他有照片時，先 `confirmDialog`「○○ 已有照片，移除後那些照片會標為『未指定』。要繼續嗎？」；**帳沒有任何檢查**。照片的檢查只看這一趟（`submissionsOfTrip(tripId)`），但旅伴是**群組**層級的。
- **群組與旅程**：app 內建立的旅程每趟新建一個群組（`create.js` 約 272 行）；加入別人的旅程沿用同一個群組。實務上一個群組一趟，但照群組算才不會漏。
- **結清**：`settleTrip` 用 `membersOf(trip.groupId)` 當成員名單；`settleCore` 的 R4（v1.74.5）把「付款人不在名單裡」當成沒有付款人、整筆不進淨額，但他在別人那筆的分攤照扣。畫面 `nameOf()` 在 `members` 裡找不到就寫「（未指定）」；「每個人」只列 `members`。
- **你 v1.74.5 的實測**（自己造的資料）：移除小美後，她付的 90 元寫成「有 1 筆沒有付款人」、明細「（未指定） 付」；她在阿公那筆晚餐的分攤 100 元仍在帳上 → 結清方案「（未指定） 給 阿公 NT$100.00」，「每個人」不列她。

## 2. 目標與非目標

**目標**：G1 移除前，使用者知道他有幾筆帳、移除之後會怎樣；G2 移除後，帳面仍叫得出他（「小美（已移除）」），他付的錢照樣算，淨額仍守恆，不再出現「（未指定）」；G3 不改資料結構、不動同步、不新增畫面元件（沿用既有的 `confirmDialog` 與既有的列表樣式）。

**非目標**：不擋移除（使用者看完提醒仍可移除）；不自動把他的帳改成別人付或刪掉；不做「恢復已移除的旅伴」；不改照片的「未指定」行為（R1 只把照片的檢查範圍改成群組）；不動 `workers/`、`server/`、`merge.js`、同步格式、任何資料欄位。

## 3. 規則

- **R1 移除前的確認（合併成一個對話框）**
  - 算這個**群組所有旅程**裡：他付的筆數、他參與分攤的筆數（兩者都算的那筆只算一次也行，但要講得出兩個數字各是多少）、他的照片數（照片的檢查範圍一併從這一趟改成整個群組）。
  - 三樣都是 0 → 跟現在一樣直接移除，不跳對話框。
  - 有帳 → 用既有的 `confirmDialog`（`danger: true`）講三件事：①他有幾筆帳（付了幾筆、分攤幾筆）；②**移除之後這些帳照樣算，結清方案會寫成「○○（已移除）」**；③如果是記錯了，先到分帳把那幾筆改掉再移除。有照片就在同一個對話框再講照片那一句。按鈕「移除」「取消」。措辭你定，意思要到；不准用「可能會對不上」這種講不清楚的話——有了 R2，錢是對得上的。
- **R2 移除後，帳面照樣叫得出他**
  - `settleTrip` 傳給 `settleCore` 的成員名單，**包含這個群組已移除的旅伴**（`type === 'member'`、同一個 `groupId`、`deleted: true` 的墓碑）。R4 的「付款人不在名單裡」因此收窄成「**連墓碑都沒有的 id**」才算沒有付款人。→ 他付的錢照樣進結清，守恆不變。
  - 名字：現在的成員照舊；已移除的旅伴用墓碑上的 `displayName`，後面加「（已移除）」；連墓碑都沒有的 id 仍寫「（未指定）」。**做成一個查名字的函式，分帳頁的結清方案、「每個人」、明細副標「○○ 付」都用它**，不要各處各寫一份。
  - 「每個人」那一區：現在的成員照舊列；已移除的旅伴**只有在這一趟有帳時才列**（付過錢，或淨額不是 0），排在現在的成員後面、名字後加「（已移除）」。
  - 需要「這個群組已移除的旅伴」時，在 `js/store.js` 加一個**唯讀**的選擇器（例如 `formerMembersOf(groupId)`）；不改任何寫入、同步、資料結構。你若認為用既有的 `getRaw` 就夠，照你判斷，回報理由。

## 4. 與現有規則的交互

| 現有的東西 | 會不會衝突 | 結論 |
|---|---|---|
| R4（v1.74.5）「付款人不在名單裡 → 沒有付款人」 | **語意收窄** | 已移除的旅伴不再算「沒有付款人」；只有完全不認得的 id 才算。既有斷言用的若是完全不認得的 id → 照舊；若用的是已移除的旅伴 → 改成新語意（照算、不計入 `noPayer`），**不是刪**。「有 N 筆沒有付款人」的提示照舊 |
| R5（v1.74.6）整數化 | 不會 | 已移除的旅伴也是 `balances` 的一員，照樣整數化、參與殘差分配 |
| 守恆 | 不會 | 本來就守恆；現在只是他付的錢也算進來、名字叫得出來 |
| `settletest` 的 `WANT`、`moneytest` 的 M5／M6、T1–T11 | 不會 | **一字不改照樣綠**——回歸底線 |
| 照片的確認 | 合併 | 同一個對話框講兩件；照片檢查範圍改成群組 |
| 群組的邀請、加入、`claim.js` 的挑成員 | 不動 | 那些只看現在的成員（`membersOf`），不要讓已移除的旅伴出現在任何挑人的清單裡 |
