### 交通方式的細節（2:1 與分歧處理）
- 放在**到達站**的 spot 上，同時記**選的時候的前一站 id**。畫面只在「現在的前一站＝記下的那一站」時顯示所選方式；站被重排、前一站被刪、換了天 → 顯示通用圓點（不把舊選擇套到沒選過的一段——三票都點名這是最大的錯法）。每天第一站沒有進站段、不給選。
- 欄位：兩個純量 `legFrom`、`legMode` 放同一組 `leg`（代理 3 的形狀；代理 1 是一個物件欄位，語意相同）。選純量是因為合併、清洗都以欄位為單位，比物件好驗。
- 選項：程式寫死代號 `walk／train／bus／car／boat／plane／other`，只存代號；認不得的代號（未來版本新增的）一律通用圓點、不顯示任何字。
- 少數票（另開型別）的擔心照樣守：重排／刪站後不得殘留顯示 → 一條斷言＋突變（代理 3 也要求：拿掉 `legFrom` 比對、重排後必須紅）。少數票指出的「複製／分享行程時 spot id 會換新」（`share.js`）同樣適用於 `legFrom`：複製時要把 `legFrom` 一起對應成新 id，否則只是退回圓點（不會顯示錯的）。

### 當日花費的細節
- 舊花費一律「沒有標第幾天」，當日合計下方照實寫「另有 N 筆沒標日期」。
- **表單要不要預選「今天是第幾天」有分歧**：代理 2、3 可以（只在今天落在行程日期內、畫面看得到、可改）；代理 1 可以但接受完全不預選。分歧採保守 → **先不預選**，留空讓使用者選（「不用預設值冒充使用者輸入」）。要預選再問 Yolin。
- `expense` **不能**進 `TRACKED`（三票都讀程式查到）：舊版 `patch` 只在型別有欄位組時才更新 `_f`，改成追蹤型別後，舊手機改金額會帶著舊 `_f` 上傳、每一組都輸掉，真實修改被丟掉（`merge.js` 87–90 行的警告）。

## 部署順序與風險（三票共同）
1. `merge.js` 的 `TRACKED.spot` 加三組：`leg`、`important`、`booked`。`expense.day` 不動 `merge.js`。
2. **Worker 先部署、客戶端後推**（CLAUDE.md 常設規則；v1.73.2 實測反過來會永久分歧）。D1 結構不用改（整筆存在 `json` 欄）。
3. 沒有資料遷移；沒有任何一步會刪除或改寫使用者看得到的值。
- **要先實測的一點（代理 1、3 都指出，推論沒驗）**：新的合併規則對「兩邊都沒有這組」的記錄會在 `_f` 補上 `leg:0` 等鍵；代理 3 推論這可能讓新客戶端觸發「修復推送」、Worker 把只差 `_f` 中繼資料的 spot 寫回 D1、各佔一個 seq（值不變）；代理 1 推論只在本來就會寫入的時候發生（跟當初加 `dayStarts` 一樣）。**部署前用 `workertest` 重現，看哪一個對**；會寫回 D1 的話，那是對家人群組的寫入，照 CLAUDE.md 先問 Yolin。
- 查不到的：線上 Worker 是哪一版、家人手機跑哪一版（v1.56 以前沒有 `_f` 的版本推上來可能蓋掉新值——代理 1）。

## 推論、沒驗的
三票的相容性表格都是逐行讀程式推出來的，沒有執行；舊客戶端遇到新欄位時其他畫面（回顧、統計）會不會出錯，沒有逐一查。
