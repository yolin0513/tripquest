# 架構決策：多人同步的後端、身分與照片儲存

- 日期：2026-09-05
- 方法：3 個獨立的 Opus 代理各自評估、投票，多數決，分歧採保守方案。
- 結果：**三項決策，三位代理全數一致。**

---

## 決策一 —— 託管與後端：**Cloudflare Workers + R2 + D1**（自架 + Cloudflare Tunnel 為退路）

### 用量估算（一趟旅行）

| 項目 | 數量 |
|---|---|
| 成員 × 任務 | 5 人 × ~20 個 |
| 照片（去重、壓縮後） | ~150–250 張，每張 ~350 KB |
| 縮圖 | ~150–250 張，每張 ~20 KB |
| 每趟儲存量 | 全圖 ~50–90 MB＋縮圖 ~4 MB |
| 每趟同步流量（縮圖先傳、全圖點閱才傳） | **必要流量 ~20–40 MB**；若每個人都點開每張全圖，尖峰 ~450 MB |
| 一年 3–10 趟 | 儲存 ≤1 GB/年、流量 ≤5 GB/年 |

這個工作負載是「**流量偏重、儲存量小**」，且旅行是季節性的（一年數趟、平時完全不用）。這兩點決定了選擇。

### 選定：Cloudflare Workers + R2 + D1

| 免費額度 | 我們的用量 | 餘裕 |
|---|---|---|
| Workers 100k 請求/日 | ~5k/趟 | 20× |
| Workers 請求 body 上限 100 MB | 每張照片 0.35 MB | 285× |
| R2 儲存 10 GB | ~90 MB/趟 → 約 110 趟 | 十年份 |
| R2 Class A 寫入 100 萬/月 | ~500/趟 | 2000× |
| R2 **對外流量費：$0（永久）** | — | 這是關鍵 |
| D1 5 GB、每日 10 萬列寫入 | ~500 列/趟 | 不成問題 |

**為什麼是它：**
1. **R2 對外流量完全免費** —— 照片同步 App 最怕的就是流量費爆掉，這條讓「不小心寫錯上傳迴圈」也不會產生帳單。
2. **永遠開著** —— 不需要一台電腦保持開機。長輩在墾丁玩到晚上 10 點，家裡的 PC 剛好在跑 Windows Update，沒人能處理 —— 這個失敗情境直接消失。
3. **邊緣節點離台灣近** —— 行動網路延遲低。
4. **貼合現有架構** —— 現有的 `SyncAdapter` 介面（`push` / `pull` / `putBlob` / `getBlob`）可以幾乎 1:1 對應成一個約 150 行、無相依、無打包的 Worker 檔（`workers/worker.mjs` 已寫好）。維持「開檔即跑、不打包」的精神。
5. 靜態 App 本身也能由 Workers 的 Static Assets 一起託管 → 只有一個網址、沒有 CORS 問題（GitHub Pages 可保留為鏡像或退役）。

**唯一的門檻：啟用 R2 需要在帳戶綁一張信用卡**（在免費額度內不會扣款）。Workers 與 D1 不需要。

### 退路（escape hatch）：自架 `server/index.mjs` + Cloudflare Tunnel

- 同一個 Cloudflare 帳號，`cloudflared` 在你的電腦跑一條 named tunnel，把已經寫好的 `server/index.mjs` 接到外網（HTTPS + 固定網址，解決浮動 IP）。
- **零改寫**：`LanAdapter` 就是 `CloudAdapter` 少一個 base URL 的差別。
- 代價：電腦要保持開機、可連線。適合「先驗證」或「不想綁卡」。
- **不選 Tailscale**：它要求每一支長輩的手機都安裝 VPN App 並登入帳號 —— 比密碼還麻煩。

### 被否決的方案

| 方案 | 否決理由（三位代理一致） |
|---|---|
| **Supabase 免費方案** | **閒置 7 天自動暫停**。旅行一年才幾趟、平時幾個月不開，等於每次出遊 App 都是暫停狀態，要本人登入後台喚醒 —— 對長輩是「壞掉的 App」。且儲存 1 GB 是**總量**（約 10 趟就滿）。它的賣點是內建 Auth + Realtime，但決策二選「不做帳號」，這價值歸零。 |
| **Firebase** | Cloud Storage 自 2024 年 10 月起**強制綁定 Blaze（信用卡）帳單**，且只有預算「警示」沒有硬性上限。把「必須綁卡、無硬上限」和「可能寫錯的上傳迴圈」放在一起 = 帳單風險無上限，換不到任何技術好處。 |
| **純自架 + Tunnel 當主力** | 頻寬不是問題（家用 FTTH 上傳 ~40–100 Mbps，一趟 450 MB 幾分鐘傳完），成本也不是。致命傷是**無人看管的開機率** —— 需要的當下（出遊、深夜、訊號差）沒人在電腦旁。當退路很好，當主力不行。 |

## 決策二 —— 是否需要註冊：**不需要帳號**

主要使用者是長輩，帳號密碼是最大的摩擦。

### 選定：邀請連結 ＋ 裝置身分 ＋ 自訂顯示名稱

- **加入方式**：群組建立者產生一條邀請連結（內含 128-bit 群組祕鑰，放在網址的 `#fragment` 段 —— 不會進到伺服器紀錄或 Referer）。朋友點開就加入**同一個**群組（不是複製一份）。
- **身分**：每台裝置一組穩定 ID，存在 **IndexedDB**（跟照片放一起，不是放 localStorage —— iOS 會單獨清掉 localStorage 而留著照片，造成「照片還在、但不認得是你的」）。
- **「這張誰拍的」**：照片投稿記錄裡存的是 `memberId`（成員），不是 `deviceId`（裝置）。`member` 是一般的同步記錄（含 `groupId` + `displayName`）。
- **換手機／清快取後**：用同一條邀請連結重新進入 → 出現「**這是誰的手機？**」畫面，點自己的名字 → 過去所有照片**一鍵全部認回來**（因為投稿綁的是 memberId）。
- **一人多裝置**（例如阿嬤的手機 + 平板）：新增 `memberClaim {memberId, deviceId, claimedAt}` 記錄，天然是聯集，UI 可顯示「王媽媽 · 2 台裝置」。
- **身分備份卡**：一個畫面顯示 QR + 一組短碼，編碼你的裝置身分與已加入的群組。提示使用者截圖或用 LINE 傳給自己。新手機掃一下即可完整還原。
- **有人在已被認領的名字上再點一次** → 軟性確認「你是王媽媽嗎？」，防止誤點。

### 防濫用

| 風險 | 緩解 |
|---|---|
| 邀請連結被轉發外流 | 連結是「加入權」不是「發文權」；`/pull` 依 `tripId` 分範圍（目前的伺服器沒做，已修）；祕鑰 128-bit（不是原本的 6 碼 32-bit，可被公開伺服器暴力猜）；加入需群組內既有裝置**一鍵核准**；連結可撤換、72 小時到期；大家都加入後可「鎖定成員名單」。 |
| 冒用他人身分發文 | v1：TOFU（首次綁定）—— 伺服器記住 `memberId → 裝置`，之後同一個 memberId 從別的裝置推送會被拒。**v2 強化**（2 位代理建議、1 位認為家庭群組不必要，採保守先不做）：每筆投稿用 WebCrypto ECDSA 金鑰簽章，讓歸屬完全不可偽造。介面已為此預留。 |

### 被否決的方案

- **一次性驗證碼 / magic link（email 或簡訊）**：要離開 App 去收信、等碼、回填 —— 對長輩是最高棄用率的流程。簡訊還要付費供應商 + 綁卡。
- **傳統帳密**：摩擦最大，且「忘記密碼 → App 等於死掉」對這個族群是常態。
- **第三方登入（LINE / Google / Apple）**：LINE 在台灣長輩間近乎人人有，最誘人；但 iOS standalone PWA 的 OAuth 轉導常常掉 session，且要過 LINE 開發者後台。五個彼此認識的家人出遊，這些防的是不存在的威脅。

## 決策三 —— 照片儲存策略

| 項目 | 決定 |
|---|---|
| **壓縮** | 維持 1600px 長邊 / JPEG / 品質 0.82（~350 KB）＋ 320px 縮圖（~20 KB）。WebP 只在執行期探測 `canvas.toBlob('image/webp')` **確實回傳 WebP** 時才用（Safari 不支援時會默默吐 PNG，1600px PNG ~3 MB），並把實際 mime 記在 blob 記錄上。不用 AVIF（前端編碼太慢）。 |
| **原檔** | 相機原檔**永不同步、預設不保留**。 |
| **同步分層** | **縮圖：全部立即同步**（~4 MB/趟，爛訊號下也一分鐘內完成，相簿馬上能看）。**全圖：延遲同步** —— 點開看大圖時、或連 Wi-Fi 時背景抓、或做回憶影片時才抓。把「必要流量」從 ~300 MB 砍到 ~20–40 MB/趟。 |
| **離線佇列** | IndexedDB 新增 `outbox` store（`{id, op, hash, tries, nextAt, lastError}`），**在拍照當下就寫入**（不是在同步時），UI 立刻標記完成。抖動指數退避（8s → 5 分，含 ±30% jitter）。Android 用 SW Background Sync，iOS 用 `online` + `visibilitychange` 事件驅動。畫面只出現一個平靜的「N 張待上傳」小標，不出現錯誤碼、不跳 modal。**PUT 前先 `HEAD /blob/:hash` 確認不存在才上傳** —— 修掉「每次同步重傳所有照片」的 bug。內容雜湊定址讓每次重試都是冪等的、可續傳的。 |
| **同步游標** | 改用**伺服器指派的單調遞增序號**，不再用客戶端的 `Date.now()` —— 修掉「兩支手機時鐘差幾秒就永久漏記錄」的 bug。 |
| **空間上限與清理** | 首次匯入照片時（而非冷啟動時）呼叫 `navigator.storage.persist()`。用 `navigator.storage.estimate()` 在 60% 提醒、90% 擋下新匯入。清理階梯（永遠不動當前旅程、最舊的先清）：丟保留的原檔 → 丟 90 天前、已做過影片的旅程的全圖（**保留縮圖**，相簿仍完整，點開會從 R2 重抓）→ 才提示整趟封存（強制先匯出備份）。R2 端設 180 天 lifecycle rule。 |
| **EXIF / GPS** | 維持「重新編碼順帶清光」的預設（結構性的，不是可能漏的過濾器）。GPS 僅在該行程手動開啟時保留，**四捨五入到小數點後 3 位（~110 公尺）** —— 目前是 5 位（~1 公尺、到住家門口等級），已改。行程關閉 GPS 開關時，回頭把已存座標清空。 |
| **刪除照片** | `deleteSubmission` 改為寫「撤回墓碑」記錄，不硬刪 —— 否則聯集合併時會在其他裝置復活。 |

## 現有程式碼中發現、且已修或待修的缺陷（三位代理獨立指出）

| 位置 | 問題 | 處理 |
|---|---|---|
| `js/sync.js` 舊 blob 迴圈 | 每次同步把「本機已有的」照片**全部重傳一次**（200 張 ≈ 90 MB／次／裝置） | ✅ 改用 `outbox` 佇列，只送待送項目、成功即刪；PUT 前 `HEAD` 檢查 |
| `js/sync.js` 同步游標 | 存 `Date.now()`（客戶端時鐘），時鐘差就漏記錄 | ✅ 改用伺服器回傳的序號 |
| `server/index.mjs` | 無驗證、CORS `*`、`/pull?since=0` 回傳所有群組的所有記錄 | ✅ 加群組 token 驗證 + 依 `groupId` 分範圍（Worker 與 fallback server 都做） |
| `js/exif.js` | GPS 存到小數 5 位（住家精度） | ✅ 改 3 位 |

## 風險與緩解

| 風險 | 緩解 |
|---|---|
| R2 啟用需綁卡，使用者不願意 | 退路：自架 `server/index.mjs` + Cloudflare Tunnel（不需綁卡），或維持純單機（分享連結 + 備份檔）。App 三種模式都支援，設定頁一鍵切換。 |
| Cloudflare 免費額度政策未來改變 | 資料無鎖定：`server/index.mjs` 是同一份資料模型的完整實作，隨時可搬回自架。R2 相容 S3 API，可搬到其他物件儲存。 |
| Worker 部署對非工程師有門檻 | `SETUP_TODO.md` 有逐步指令；`wrangler.toml`、D1 schema、Worker 程式碼都已寫好，理想情況是三行指令。 |
| 出遊中完全沒網路 | 一切照常離線可用（單機模式的所有功能）。照片進 `outbox`，回到有訊號時自動補傳。回憶影片、相簿頁完全離線可做。 |
| 長輩把邀請連結貼到公開群組 | 128-bit 祕鑰 + 加入需核准 + 可撤換 + 可鎖定名單。最壞情況是有人看到家庭旅遊照，非財務或帳號風險。 |
| iOS 7 天清除本機資料 | 首次匯入呼叫 `persist()`；提示加到主畫面；照片一旦上傳到 R2，換裝置或被清掉都能重新拉回。 |

## 落地順序

1. **本週可做（不需你的憑證，已完成大部分）**：`outbox` 離線佇列、`HEAD` 去重、伺服器游標、`server/index.mjs` 加驗證與分範圍、`CloudAdapter`、Worker 程式碼與 schema、身分存進 IndexedDB、「這是誰的手機？」加入畫面、邀請連結（128-bit / fragment）、WebP 探測、GPS 精度、撤回墓碑、設定頁同步 UI。
2. **你明早做**（見 `SETUP_TODO.md`）：註冊 Cloudflare、`wrangler deploy`、（若接受綁卡）啟用 R2。約 45 分鐘。
3. **部署後我做**：對著你的實際網址跑一次端到端測試，補 Worker 端細節。
4. **v2 之後**：投稿簽章、Realtime 推播（改用 Durable Objects 或 SSE）取代輪詢。
