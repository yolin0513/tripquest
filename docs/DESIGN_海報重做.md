### 2-5 P2 照片的細設計（2026-10-27，只有設計、沒寫程式；資料面全部是讀程式得到的，沒有實測）

**一、讚數的資料：有，在哪，可不可信**〔讀程式〕

- **在哪**：每一個讚是一筆 `type: 'reaction'` 紀錄（`store.toggleReaction`），帶 `submissionId`、`actorId`；跟著群組同步；`store.reactionsOf(subId)` 取。照片牆、檢視器、`memory.js` 的精華版都已經在用它。
- **可不可信——三個問題**：
  1. **取消讚不會同步**。取消讚是在本機硬刪那一筆（`db.deleteRecordHard`）；但 `reaction` 在 `merge.js` 是只增不刪（`APPEND_ONLY`），Worker 也沒有刪讚的路徑，所以**已經同步出去的讚，在別人的手機上永遠還在**；拉資料是增量的（`seq` 游標），自己這台通常也不會再拿回來。結果：同一張照片，各台手機的讚數可以不一樣；數字是「曾經有人按過」，不是「現在有幾個讚」。撤回照片用的是另一筆 `retraction` 紀錄（只增不刪也能撤回），讚沒有對應的做法。
  2. **同一個人可能算兩次**：同一人在兩台手機各按一次（離線時），會是兩筆；`reactionsOf` 不依人去重。
  3. 自己按自己的照片也算。
- **怎麼用**：**數「按過讚的不同的人」**（`actorId` 去重，沒有 `actorId` 的不算），只拿來決定先放哪一張，**海報上不印讚數、也不寫「最多人按讚」這類話**——排錯的代價是「放了另一張家人拍的照片」，不是印出一句錯的話；寫出來的話就是主張，數字不可信就不能主張。
- **問題 1 本身是 App 的 bug**（照片牆的 ❤️ 數也是錯的），**不在 P2 修**：要修得加一種「取消讚」紀錄，動到 `merge.js` 與 Worker 的同步語意，屬於要投票的資料結構變更，而且 Worker 要先部署。列給 Yolin。

**二、挑照片的順序（每一層都是可以查證的事實，沒有「照順序猜」）**

候選：那一天（封面是整趟）所有景點的使用者照片，去掉撤回的、依雜湊去重。依序比：

1. 按過讚的不同人數，多的先；
2. **清不清楚**（見第三點，量出來的），清楚的先——放在讚數後面，所以讚多的不會因為糊就被換掉，只在讚數相同時才讓清楚的贏；
3. 拍攝時間早的先（`takenAt`，沒有就用建立時間）；
4. 最後用紀錄 `id` 排，保證同一台手機同一份資料每次挑得一樣（平手時不會隨機換）。

- **都沒有讚**時就是第 2～4 層，等於「清楚的、拍得早的那一張」。這個退路**不暗示任何意義**：畫面上沒有任何字說這張是「精選」「最多人喜歡」，所以挑哪一張都不是錯資訊。
- 第 3 層是任意選的偏好（不是「比較好的照片」），寫在程式註解裡講明，免得下一個人以為它有意義。
- 副照片（D3）＝同一排序的第 2、3 名，不重複主照片；不足就只放有的（P1 已是這樣）。
- 使用者照片一張都沒有，才輪到示意圖（貼「示意圖」），再沒有是色塊＋站名（P1 已是這樣）。
- **不做**「讓使用者自己指定封面照片」：那是新功能、要存新欄位（資料結構），P2 不做；有需要另列。

**三、只有縮圖時：先補、再講明、讓人選，不默默放上去**

- **現況**〔讀程式〕：海報現在**一律先用 320px 縮圖**（`pickPhotoHash` 取 `thumbHash || photoHash`），連本機有 1600px 全圖時也用縮圖——P2 第一步就是改成全圖優先。`blobURL(photoHash)` 本機沒有會自己去伺服器抓（`lazyFetch`）；離線、沒開同步、對方還沒傳上去就抓不到。
- **「糊不糊」用量的**：解碼之後拿照片的實際像素，跟它要放的那一格（C4 960×640、D2 960×590、D3 每張約 470 寬）比；要放大超過 1.5 倍才算「會糊」。不看是哪一種雜湊——示意圖的尺寸我不知道，量的才對得上。1.5 是起點，要看截圖再定（〔推論〕320px 放到 960 寬是 3 倍，一定算；1600px 不會）。
- **流程**：
  1. 按「產生」→ 先把每一張用得到的照片拿全圖（本機沒有就去抓）；
  2. 抓完還有會糊的 → **產生之前**跳一段說明，不是彈窗、是海報頁裡的一段字，講清楚哪幾張、為什麼：「封面、第 2 天的主照片在這支手機上只有小圖，印出來會糊（拍照的人那邊的完整照片還沒傳上來，或這支手機沒連上網）」，三個按鈕：
     - **「重新下載完整照片」**（再抓一次，跟照片牆的「重新下載」同一條路）；
     - **「換清楚的照片」**（那一格改用排序裡下一張清楚的；沒有清楚的就不給這個按鈕，**不假裝有得換**）；
     - **「照樣產生」**。
  3. 預覽也照同一套挑法，畫面跟成品一樣；預覽上會糊的那一格，格子下方的頁面文字（不是海報上）寫「這張是小圖」。
- **海報上不打「小圖」標記**：海報是要留下來、分享出去的東西，「這張比較糊」是畫質，不是內容錯了；該知道的是做海報的人，在產生之前就讓他知道、讓他選。**不縮小顯示**：格子是固定大小，縮小就是留空洞（P1 的「不留空洞」）。
- 我的建議：**預設不替使用者換**。「換清楚的」會把讚多的那張換掉，那是使用者的取捨，給按鈕、不自動做。

**四、P2 的程式切法（照 P1：能在 node 測的放純函式）**

- `layout.js` 新增純函式 `rankPhotos(cands)`（排序四層）與 `isBlurry(natW, natH, boxW, boxH)`；候選由 `modelFrom` 給（每張帶 `likers`＝去重人數、`hasFull`、`takenAt`、`id`）。
- 「清不清楚」要解碼才知道，所以分兩段：先用 `w/h`（照片紀錄存的全圖尺寸）與「本機有沒有全圖」做第一輪排序，抓完、解碼之後用實際像素再判一次；兩段的結果不一樣時以解碼後的為準，並寫進測試。

**五、P2 要寫的測試（每條先寫、先證明會紅；排進待驗清單 G 節）**

- node：讚數多的先；同一人兩筆只算一次；沒有 `actorId` 的不算；平手時清楚的先；都沒讚時拍得早的先；全部相同時依 `id`、每次一樣；撤回的照片不進候選；副照片不重複主照片；`isBlurry` 的界線（1.5 倍剛好、剛超過）；有全圖時用全圖不用縮圖（現況是反的，這條修正前一定紅）；模型與畫的那一半都沒有讚數字。
- 瀏覽器（重負載、要許可）：只有縮圖的行程，按「產生」→ 說明那段看得到、列的是對的那幾格；「換清楚的」沒得換時不出現；「照樣產生」產得出來；有全圖的行程不出現說明。
- 突變：不去重人數、讚數不排序、清楚度排在讚數前面、拿掉 `id` 那一層、縮圖優先（回到現況）、說明不出現、沒得換也給「換清楚的」按鈕。

## 3. 主題那條規則，在新版怎麼貫徹

**規則**：景點沒帶 `theme`，就不印類別名（`storedThemeOf`；2026-10-27 主題章修正）。新版再往前一步，照 10/27 定的「配色是裝飾、插圖與文字是主張」：

| 東西 | 是裝飾還是主張 | 新版怎麼做 |
|---|---|---|
| 類別名（「🌿 山林自然」） | 文字＝主張 | **整個不印**——新版版面沒有主題章這一區。比「有帶 theme 才印」更嚴：帶著的 theme 也可能是 v1.74 以前存下的猜測（舊資料沒查），而海報不需要它 |
| 主題插圖（鳥居、碗筷、山、燈籠……） | 插圖＝主張 | **不用**。裝飾只留跟內容無關的：波浪、虛線、紙紋、圓點 |
| 每站 emoji | 圖示＝主張 | **不印**（舊資料可能是猜的） |
| 配色（重點色） | 裝飾 | 跟著 `trustedThemeOf(整趟)`（從景點庫重算；`storedThemeOf` 已作廢——存著的 theme 也是猜的）；沒有就用和紙的預設色。顏色不說任何事 |
| AI 每天一句 | 文字＝主張 | 只印快取裡還在的；猜出來的那幾天依 Yolin 選的 (a) 清掉（乾跑 `scripts/aicache-dryrun.mjs` 已寫，等權限跑） |

**Dispatch 2026-10-27 最終裁定**：海報一律不印類別，**連可信類別也不印**；可信類別只決定配色。現行海報已先照做（主題章、主題插圖、時間軸樣式、每站 emoji 都拿掉，`postertruthtest` P2／P8／P9），P1 沿用。

**守門（寫進測試，見第 5 節）**：海報模型整份不含任何主題類別名；畫布上不呼叫任何 `THEME_DECO` 的插圖；`guesscensustest` 的登記照舊——新版若要再呼叫 `themeForSpot` 等，必須登記用途，`label` 這種用途本來就不准登記。

## 5. 測試計畫（寫程式時照這個做；每條先寫、先證明會紅）

- **模型層（秒級、不開瀏覽器）**，從 `modelFrom` 的輸出驗：
  - 不帶 `theme` 的景點**與帶著 `theme` 的景點**，模型裡都沒有任何類別名（新版不印主題章，兩種都要驗，否則只驗到一半）；
  - 模型裡沒有 `emoji`、沒有每站介紹欄位；裝飾清單裡沒有任何 `THEME_DECO` 的名字；
  - 照片挑選：讚數多的先；只有縮圖時回報張數；示意圖帶 `user: false`；
  - 一天 6 站 → 時間軸 5 行＋「還有 1 站」（固定上限不能無聲吃掉資料）；沒填時間的站沒有時間字；
  - 沒有出發日 → 沒有日期字；沒有 AI → 沒有副標與每天一句。
- **畫面層（開瀏覽器、重負載、要許可）**：從「回顧 → 做海報」真實入口；輸出尺寸是 1080×1350；張數＝天數＋1；只有縮圖時提示字看得到；字對底的對比 ≥ 4.5（canvas 讀像素）。
- 每條一個突變（例：主題章加回來、emoji 加回來、示意圖不貼標籤、截斷不寫「還有 N 站」、讚數不排序）。
