# 建議：伺服器上刪群組不持久——對「移除旅伴」「重設邀請連結」的意思（給統籌者）

> 開發 Session 2026-09-25 寫，**只查、沒改任何程式**。這不是規格，是寫規格用的材料與建議；規格由統籌者寫。
> 標「確認」的是讀程式碼或對正式 D1 唯讀查詢得到的；標「推論」的沒有實測。

## 一、查到的事實

1. **群組會自己長回來（確認）**：Worker 的 `/push` 與 `PUT /blob/` 遇到不存在的群組，會用**這次請求帶來的祕鑰**建立它
   （`workers/worker.mjs` 的 `authGroup(…, { createIfMissing: true })`）。設計目的是讓第一次推送就能開群組。
   實例：2026-09-24 刪掉的 4 號「測試」，之後被一台還留著那個行程的裝置推回來——群組 ID、28 筆記錄 ID、3 台裝置都相同。
   截至 2026-09-25 03:07（台灣時間）查詢，被刪的 17 組裡只有這一組長回來。
2. **群組 ID 可以被佔走（確認）**：群組列一旦不在，**任何知道群組 ID 的人**都能用自己挑的祕鑰先推一次，把那個 ID 建成他的。
   群組 ID 寫在邀請連結裡。
3. **佔走之後家人的資料不會被污染，但那個 ID 從此不能用（確認）**：佔走的人設的是他自己的祕鑰；家人裝置拿舊祕鑰拉、推都會
   收到 403。拉的那段遇到失敗就當成「這次拉不到」，不會合併任何東西（`js/share.js`）；推的那段會把那筆標成送不上去，
   顯示「這台手機的同步權限被拒（祕鑰可能換過了）」（`js/outbox.js`）。拿舊邀請連結加入的人會看到「這個連結好像不完整」。
   **另外（推論）**：佔走的人用他的祕鑰可以讀那個 ID 底下還留在 R2 的照片——但要知道照片的雜湊才讀得到（只有看過那趟行程
   資料的人會知道）。已刪的 26 組目前在 R2 沒有剩下的照片（1 號那 10 張 2026-09-25 清掉，其餘各組本來就沒有或沒傳上去）。
4. **Worker 沒有任何端點會換祕鑰或刪群組（確認）**：對 `groups` 表的改動只有「序號加 1」。刪群組只發生在我們手動操作 D1 時。
5. **「移除旅伴」不收回權限（確認）**：做法是在那筆旅伴記錄立墓碑（`deleted: true`）再同步；所有裝置共用同一把祕鑰，伺服器分
   不出是誰，被移除的那台照樣拉得到全部資料、推得上去。

## 二、對現有功能的意思

**移除旅伴**——三種情形：
- 被移除的裝置只是重推舊版本：**不會**加回去。旅伴記錄走整筆「後寫入者勝」（`js/merge.js`：`member` 不在逐欄合併的表裡），
  墓碑比較新。（確認：讀程式碼）
- **它離線時改了自己的旅伴資料（名字、電話），之後才推上來：旅伴會復活**——那一筆的時間比墓碑新，整筆蓋過墓碑。
  這是真實會發生的情境：長輩的手機常常離線，改完名字、幾天後才連上。（推論：沒實測）
- 再用邀請連結加入一次：會建一筆新的旅伴記錄。（推論）

**重設邀請連結**（還沒做；Yolin 要保留）：
- 如果做成「刪掉群組、開一個新的」：舊裝置一推，**舊群組就用舊祕鑰長回來，舊連結照樣能用**——一個宣稱能重設、實際上舊連結
  還能用的功能，比沒有這個功能更糟。
- **原地換祕鑰、不刪群組列**才擋得住：群組列還在，舊祕鑰推送會被 403 擋下，不會觸發自動建立。（推論：功能還沒做）

**刪除群組本身**：刪掉的那一刻起，那個 ID 就是一個可以被接管或被舊裝置復活的視窗。

## 三、建議（給寫規格用）

1. **重設邀請連結＝原地換祕鑰**：新端點（例如 `POST /rotate`）用**目前的祕鑰**授權，`UPDATE groups SET secret = ?`，**絕不刪群組列**。
   換完之後，還拿舊祕鑰的裝置會收到 403——要想清楚家人其他裝置怎麼拿到新祕鑰（例如：換的人重傳新連結、各裝置重新加入），
   以及 403 時畫面要講什麼（現在講的是「祕鑰可能換過了」，剛好對）。
2. **刪除群組改成留墓碑列**：不要真的 `DELETE FROM groups`；改成群組列留著、標成已刪除（或祕鑰換成不可能的值），
   `authGroup` 看到已刪除就回 410、**不自動建立**。這樣刪掉的群組不會被舊裝置復活，ID 也不會被佔走。記錄與照片照樣可以清掉。
   （要同時改 `workers/worker.mjs` 與 LAN 的 `server/index.mjs`；照 `CLAUDE.md`，動到 `workers/` 要 Worker 先部署、客戶端後推。）
3. **旅伴墓碑改成「刪除優先」**：旅伴一旦立了墓碑，比它新的非刪除版本也不能蓋回來，除非是明確的「恢復」動作。這是
   `js/merge.js` 的合併規則（客戶端、Worker、LAN 三處共用同一份），改之前要照 v1.73.2 的教訓評估既有資料。
4. **真正把人請出群組**只能靠換祕鑰（第 1 條）＋把新連結只給留下的人——移除旅伴本身做不到，文案不要暗示它做得到。
5. **已經刪掉的群組 ID 怎麼辦**（這件要 Yolin 決定，動 D1 要他同意）：確定傳出過邀請連結的是 9/24 刪的 3、4、6、18 號
   （群組裡有兩台以上裝置＝有人用連結加入過）；4 號已經長回來。3、6、18 號可以用第 2 條的墓碑列先佔住。其餘 13 組只有一台裝置，
   查不到連結傳出去的證據（傳了但沒人點的連結本來就查不到）；9/25 刪的 9 組是 `livecheck-import` 建的，那支腳本從不分享，
   沒有產生過邀請連結。（資料來源：兩份刪前備份，判準附對照組；不列 ID。）

6. **既有的 26 組已刪群組怎麼辦**（2026-09-24 刪 17 組、09-25 刪 9 組；其中 4 號已經長回來、現在是一組正常的群組）。第 2 條只管
   「以後刪除改成標記」；已經刪掉的那些現在是**真的不存在**，隨時可被佔走、也可被舊裝置復活。三種做法：

   | 做法 | 做了什麼 | 代價 |
   |---|---|---|
   | A. 全部補墓碑列 | 第 2 條上線之後，替 25 個 ID（4 號除外）各補一筆「已刪除」的群組列 | 要寫 D1（動真實資料庫，要 Yolin 同意）；25 個 ID 要從備份取（備份在 `.logs/`、不進版控）。之後這 25 個 ID 不能被佔走、也不會長回來——**包括還留著那些行程的裝置**：它們推送會收到 410，畫面要講清楚（例如「這趟行程已經從雲端移除」），不然家人會以為壞掉 |
   | B. 只補確定傳出過邀請連結的 | 只補 3、6、18 號 | 代價最小；其餘 22 個靠「查不到傳出去的證據」——但**查不到不等於沒有**（傳了沒人點的連結查不到），留著一點風險 |
   | C. 接受風險、不補 | 什麼都不做 | 風險說明：佔走的人拿不到任何家人資料（祕鑰不符拉不到；已刪群組在 R2 已沒有照片）；最壞的後果是「那個 ID 不能再用」＋「還留著那趟行程的裝置同步失敗」。這些群組都是測試或已放棄的行程，家人不會再用。代價是風險沒關掉，而且之後每刪一組就多一個 |

   **建議 A**（等第 2 條的墓碑機制上線再一起做，不要先用別的方式臨時佔住——臨時佔住等於又建了一組有祕鑰的群組，要另外保管那把祕鑰）。
   在那之前是 C 的狀態：風險如上，這幾天之內沒有能做、又不增加新風險的補救。
7. **驗證線上功能的腳本，不該在正式環境建真實資料**。`livecheck-import` 每跑一次就在正式站建一個行程、進而開一個群組
   （2026-09-24 一個下午留下 9 組）。上一輪說的「跑完自己清掉」要**刪群組**——而刪除本身就開一個可被佔走、可被復活的視窗，
   等於每跑一次開一個。別的做法（由輕到重）：
   - **a. 不讓它的資料上雲**：它驗的是「匯入流程在線上版本跑得通」（解析、建立景點、策展命中），不需要同步。在瀏覽器裡擋掉
     對同步 Worker 的請求（它現在已經在**記錄**所有對外請求，改成**攔截**是同一套 puppeteer 機制的另一個開關），或建立行程時不開群組。代價：驗不到「建好之後推上雲端」那一段——
     那一段本來就不是它要驗的，`workertest` 有在本機驗 Worker。
   - **b. 用專門的測試 Worker＋測試 D1**：線上頁面指向另一個 Worker 網址。代價：多一套部署要維護；而且它驗的就不是「使用者用的那一套」。
   - **c. 繼續在正式站建、跑完用第 2 條的墓碑刪掉**：墓碑機制上線之後才安全；ID 不會被佔走，但正式資料庫會一直累積墓碑列。
   **建議 a**：最小、不留東西、不開視窗。要附一條驗法：跑完之後正式 D1 的群組數跟跑之前一樣（跑之前、之後各唯讀查一次，
   對照組是「把擋請求那一段拿掉 → 群組數多 1」——這條只在測試遠端或本機 Worker 上驗，不在正式站驗）。
   同一個原則適用其他打正式站的腳本（`sweep`、`livetest`）：**只讀，不寫**；要寫的驗證放到本機 Worker。

## 四、驗法建議（照共用慣例 §7.5(c)：寫明怎麼證明實作真的會擋）

- 換祕鑰：用舊祕鑰推送 → 403、群組列還在、`groups` 筆數不變；拿掉「群組列還在」那一道（改成刪掉重建）→ 舊祕鑰推送長回舊群組、情境紅。
- 墓碑列：刪除後用原祕鑰推送 → 410、不建立；另一把祕鑰推送 → 410、不建立（佔不走）；拿掉「已刪除就不建立」→ 兩個情境都紅。
- 旅伴復活：造「墓碑之後、時間更新的非刪除版本」推上去 → 旅伴仍是刪除；拿掉「刪除優先」→ 紅。
- 這些要進 `workertest`（用 wrangler 跑真的 Worker＋本機 D1），不要打正式站。
